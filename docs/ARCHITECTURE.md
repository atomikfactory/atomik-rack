# Architecture

> This document describes the code as it stands. Where it differs from a comment or a name in a test, the code is right.

Atomik Rack is a rack of devices joined by audio, CV and note cables, a song (clips on tracks), a console, and audio tracks, played by one real-time engine. Everything that touches files, devices or the screen is kept off the audio thread.

Rules (all hold in the `Cargo.toml` files today):

- A crate depends only on crates below it.
- `atomik-engine` and `atomik-devices` never depend on each other in production code. They meet only through `atomik-device-sdk`: the engine sees a device as `Box<dyn Device>` plus a `&'static DeviceDescriptor`. (The engine's tests use the devices as dev-dependencies.)
- The engine does not know the model or the audio files. The app turns the model into engine-native `SongInput` data, and implements the engine's `StreamSource` trait over the file reader.
- `atomik-render` is the offline composition root and `atomik-app` the live one. They share one song builder, [`project::song_input`](../crates/render/src/project.rs), so a bounce and live playback build identical engine input.
- `atomik-testkit` is only ever a `[dev-dependencies]` entry.

To check the rule yourself, read the `[dependencies]` section of each `crates/*/Cargo.toml`.

## 2. Data flow, in text

### 2.1 Patch file to WAV

```
patch.json ──Patch::from_json──► Patch ──build::build──► Graph ──Graph::compile──► RenderPlan
                                  (validated,                (devices, cables,      (order, slots,
                                   JSON-path errors)          clamped params)        prepared devices)
                                                                                         │
WAV ◄──wav::write── Vec<Vec<f32>> ◄──render_offline── Engine + EngineHandle ◄────────────┘
                                     (host blocks of --block frames, 64-frame batches inside)
```

1. **Parse and validate** ([crates/render/src/patch.rs](../crates/render/src/patch.rs)): unknown fields, bad ranges and bad ids are errors that name a JSON path. The format is in [examples/patches/README.md](../examples/patches/README.md).
2. **Build** ([build.rs](../crates/render/src/build.rs)): creates a `Graph` from an `EngineConfig`, creates each device from the registry, sets params by key (clamped, with a warning), connects the cables through `Graph::connect`, and turns every note into an On and an Off `ScheduledNote`.
3. **Compile** (`Graph::compile` in [plan.rs](../crates/engine/src/plan.rs)): re-validates every cable, orders the devices with Kahn's algorithm (ties by `DeviceInstanceId`), assigns buffer slots by liveness, calls `prepare` once per device with a seed mixed from the patch seed and the device id, re-applies the stored params and preallocates all scratch.
4. **Render** (`render_offline`): drives `Engine::render` with host blocks, pushes due notes, collects retired plans and removes the engine's 64 frames of latency.
5. **Write** ([wav.rs](../crates/render/src/wav.rs)): 32-bit float (bit-exact) or 24-bit PCM.

### 2.2 Project open, edit and live sync

```
 .atomik file ──load_project──► Document (RackDoc + undo history)
                                     │  Command ──apply──► SyncOps (what changed)
 UI events ──views──► UiAction ──AppCore──┘                    │
                                                               ▼
                         AppCore translates SyncOps into EngineSink calls
        reset → insert devices (ids 1, 2, 3 …) → routing → song → transport/loop → params
                                                               │
                              EngineSink (live: Session, tests: RecordingSink / OfflineSink)
                                                               │  wait-free queues
                                                               ▼
                                                     Engine (audio thread)
```

- The **document** ([crates/model](../crates/model)) is the single source of truth. It is pure data: no UI and no engine. `Document::apply(Command)` validates, changes the `RackDoc`, records an undo step (drag edits merge by a key) and returns `SyncOp`s. Commands cover the rack (add or remove a device, cables, params), the console, the song, the sample pool (`RegisterAsset`, the one command that is not an undo step) and `Command::Batch` (several cable commands as one undo step).
- **Ordering rules** when syncing: adding a device is insert, route, then submit the song; removing is song without its track, routing, then `remove_device`; a restart is reset, inserts, routing, song, loop, metronome. The engine applies these in queue order at batch boundaries.
- **Rack columns.** The top-level rack is shown as `RackDoc.columns` columns side by side (empty columns count; at most 32). Each `RackDevice` has a `column`, and `RackDoc.devices` stays one flat list **stable-sorted by column**, so a column is a contiguous run of it and nothing that reads the flat order (graph build, engine, console, song) knows about columns; `RackDoc::check_columns` validates the invariant. A position is a `RackSlot { column, index }` (index within the column); `RackDoc::resolve_slot` turns it into the flat index (column 0 never goes above the locked Master Section; a column one past the last appends a column in the same step). Slot commands (`Command::AddDeviceAt`, `WorkflowCommand::MoveDevicesToSlot`, `PasteDevicesAt`, `CreateInstrumentAt`, `CreateEffectAt`) and `AddRackColumn` / `RemoveRackColumn` are single undo steps built from the `Layout` and `Columns` edits and report `ViewChanged` only. `CreateEffectAt` routes as if the device above the slot (the previous device of that column) were selected, and does not route at the top of a column. A device added or moved by a flat index takes the column of the device before it. Container insides are always one column (column 0).
- **Rack columns in the view** ([ui/src/rack/columns.rs](../crates/ui/src/rack/columns.rs), [device_drag.rs](../crates/ui/src/rack/device_drag.rs)). `RackView` lays the top-level rack out as `doc.columns` columns side by side, column `c` at x = `c x (RACK_WIDTH + COLUMN_GAP)` (`COLUMN_GAP` is 32), each with its own rails and stacked from y = 0; the Audio I/O strip heads column 0 only, `content_height` is the tallest column and `content_width` covers all of them, and the horizontal origin, scroll range and clamp use that width, so a single column is laid out exactly as before. A container's inside stays one column. Every panel, hit rectangle, socket and menu position carries its column's x, so hit testing, selection, folding and cables work in any column. A move drag is two-dimensional: the pointer picks the column (nearest by x) and the index among the devices that stay in it (the slot), the drop line is drawn in that column, and the release emits one `MoveDevicesToSlot` (never a no-op; inside a container the flat `MoveDevice` / `MoveDevices` as before). While a device or a browser row is dragged, a dashed "New column" zone shows to the right of the last column; dropping past the last column uses `column == doc.columns`, which the model turns into a new column in the same undo step. A press on a device-browser row that travels past the 3 px threshold starts a `Drag::Browser`: a ghost label follows the pointer, the same drop line shows, and the release over the rack emits `CreateInstrumentAt`, `CreateEffectAt` or `AddDeviceAt` (the creation options as for the double-click, Shift inverting the route); a release over the browser or outside the rack, or Escape, emits nothing. The double-click add is unchanged. Both drags scroll the rack when the pointer is within 48 px of an edge of the rack area (speed up to 700 px/s, horizontal and vertical): the host calls `RackView::tick(now_seconds)` from `Shell::frame_at` (the first tick of a drag only starts the clock, each step is at most 50 ms, so it is deterministic under test) and keeps ticking while `is_auto_scrolling()`. The rack context menu has Add Column and Remove Column (`rack.add_column`, `rack.remove_column`; the column of the right click, disabled with one column) and runs `AddRackColumn` / `RemoveRackColumn`. While the new-column zone shows (a drag), the range includes it: a rack that fits and is centred moves left only as far as it takes to keep the zone on screen (it never moves when the zone fits beside it), and a drop is worked out in the layout of the drag. Pasting from the rack's context menu (`WorkflowCommand::PasteDevicesAt`) lands at the slot under the right click (`RackView::take_context_slot`, cleared by any other click or key); a keyboard paste with a selection lands below the selected device in its column; a container paste is unchanged. A browser plugin that is neither instrument nor effect is added at the drop slot with `PluginCommand::AddAt` (column included, one undo step). Escape ends a browser drag whichever pane has the focus (`Shell` forwards it to the rack while `RackView::is_browser_dragging`).
- **Rack navigator** ([ui/src/rack/navigator.rs](../crates/ui/src/rack/navigator.rs)). A strip `NAVIGATOR_WIDTH` (136) logical pixels wide at the right edge of the rack (below the breadcrumb bar inside a container) that `rack_area()` gives up, so nothing draws under it; a window too narrow to leave the rack 240 px hides it. It draws one uniform-scale overview of the whole content: the narrower of "all columns fit the width" and "the whole height fits", so the strip always shows every column and the viewport rectangle (the rack area's part of the rack, with the zoom) is the only moving part; a very tall rack gets small blocks (at least 1.5 px high), not a scrolling overview. Blocks are the rectangles `column_device_rects` reports (device colour, folded heights, the Audio I/O strip on column 0, an empty column as an empty slot) and are recorded once into a cached `DisplayList` keyed by the layout revision (bumped by `rebuild`) and the strip geometry; scrolling, selecting and hovering redraw only the viewport rectangle and the selection outlines, and no device panel is painted. A press outside the viewport rectangle centres it on the point, a press inside keeps the grab point, a drag follows the pointer (`Drag::Navigator`, also outside the strip, clamped to the content), the wheel scrolls as over the rack (Shift sideways). The strip never starts a device drag, and a device or browser row released over it is dropped. Inside a container it shows the container's single column. View, Rack Navigator (`view.toggle_rack_navigator`, no default key) toggles it; the choice is `show_rack_navigator` in `ui-state.json` (default on). A new `RackView` has it off, so hosts and goldens that do not ask for it are unchanged.
- **Project files** are `.atomik` JSON, format version 12 (older versions still load; version 10 added the per-note mute flag, written as an optional fifth element `true` of a note; version 11 adds the rack columns: an optional `"column"` on each top-level device, after `color`, and an optional root `"rack_columns"` after `input_channels`, both omitted for a single-column rack, so versions 1 to 10 load as one column and an unchanged single-column project differs from its v10 file only in the version line; version 12 adds the optional `"buses"` of the console, below, omitted when there are none, so a project without buses differs from its v11 file only in the version line). Patches carry no columns and no buses. Saving is canonical: save, load, save gives identical bytes.

### 2.3 Audio import

```
 drop / File ▸ Import Audio ──UiAction::ImportAudio { paths, target, tick }──► AppCore::import_audio
        │
        ▼  one worker thread "atomik-import" per drop or pick
   decode (symphonia) ─► resample to session rate (rubato) ─► content hash ─► Audio/<hash>.wav
        ─► peaks (Audio/.peaks/<hash>.peaks) ─► read back (RAM, or open a stream source)
        │  Msg over an mpsc channel, one per file
        ▼
   UI thread, every frame (AppCore::poll_background):
     RegisterAsset ─► AddAudioClip (existing track)   or   AddAudioTrack ─► AddAudioClip (new track)
     ─► SyncOps ─► song resubmitted to the engine; peaks handed to the arrangement view
```

Messages carry a generation number, so work for a document that was replaced is dropped. A `DoneGuard` always sends the completion message, even if a worker panics.

### 2.4 Playback, per 64-frame batch

```
 Engine::run_batch (audio thread)
   1. apply control messages due now   (inserts, routing swaps, song snapshots, transport, tap, tempo)
   2. record tap: copy the host input batch into the tap ring, tagged with the engine frame
   3. apply queued params
   4. song player: advance the transport (loop wraps, locates); derive the batch's TimeInfo
        (tick, ticks_per_frame, loop_wrap; song-less: a free-running tick at the engine tempo);
        notes → per-device note events; automation → params;
        audio regions → per-track playback batches   (Memory: read samples; Stream: pop the lane ring)
        publish each track's playback to its audio-track device
   5. deliver scheduled and live notes
   6. routing.process / process_parallel:  for each (device, stage) in level order
        gather inputs (summing inputs add in source order; PDC delay lines on summing cables)
        Device::process_stage (audio-track: out = playback + monitored input)
        scatter outputs, publish meters
   7. mix the metronome into the host outputs; frame += 64
```

### 2.5 Streaming

```
 EngineHandle::submit_song (non-RT) ─► one lane per audio track with a streamed asset:
        ring of 256-frame stereo chunks (2 s)  ── producer + region list ──► Streamer thread
                                             └─ consumer travels in the snapshot ──► audio thread

 audio thread:  position not a continuation (first batch, locate, new snapshot, loop change)
                  → bump the lane epoch, push a StreamRequest (wait-free)
                every playing batch consumes exactly its frames from the ring (discards outside regions);
                missing data = silence + underrun counter, never a wait
 streamer thread "atomik-streamer": polls requests every 1 ms, restarts lanes, fills each lane a few
                chunks per round by calling StreamSource::read (the app's reader over the bundle WAV)
```

### 2.6 Recording

```
 ToggleRecord ─► AppCore: plan the armed tracks' inputs from the cables interface:in_k → in_l / in_r
        │  EngineHandle::record_tap(channels, 4 s)  (control queue, starts at a batch boundary)
        ▼
 audio thread: each batch appends [engine frame (2 words), 64 words per tapped channel] to a ring
        ▼
 writer thread "atomik-record": drain (contiguous runs only) ─► Audio/rec-<pid>-<take>-<n>.wav, header
        refreshed about every half second (crash safety); a gap is written as silence
 stop or locate ─► Ctl::Finish { end frame, compensation, position function }
        ▼  split into laps (one per loop pass) ─► Bundle::add_recording per lap (hash, peaks) ─► delete the
        in-progress file ─► Msg::Recorded
        ▼
 UI thread: RegisterAsset + AddAudioClip per lap and track (one undo step each)
```

`compensation = input_latency + output_latency + 64 + user_offset`; positive means the take is placed earlier.

### 2.7 Save and bounce

```
 Save:   Document ─► pruned copy (only assets the song uses) ─► save_project text
         ─► atomic write of <name>.atomik ─► Bundle::remove_orphans(song assets + undo/redo assets)
 Save As (with audio): new folder <name>/, Bundle::copy_bundle, then the same
 Bounce: load_project ─► Bundle::open ─► load_song_assets (every asset fully in RAM, never streamed)
         ─► song_input ─► render_offline_song ─► WAV      (bit-identical for any block size and workers)
```

## 3. Inside `Engine::render`

[crates/engine/src/engine.rs](../crates/engine/src/engine.rs):

- **Batches.** Devices always process exactly `BATCH = 64` frames ([crates/core/src/lib.rs](../crates/core/src/lib.rs)). `render` accepts any host block length, including 0. It copies host input into a one-batch input FIFO and copies the previous batch's output out of a one-batch output FIFO. Each time the FIFO fills, it runs one batch.
- **Latency.** The FIFO adds a fixed latency of 64 frames (`Engine::latency_frames()`). It is part of the recording compensation. Device latency (`Device::latency_frames`) is compensated by the routing (section 5).
- **Batch order** is the one in 2.4. Control messages travel through one ordered queue (`CONTROL_QUEUE_CAPACITY` = 1024), so "insert A, then a routing that uses A" is always applied in that order.
- **Per device**, in routing order: zero the device's output scratch (so outputs arrive zeroed and unconnected inputs read zeros), gather cabled inputs, merge cable notes with scheduled notes, call `process_stage`, scatter the outputs to slots.
- **No routing.** The engine outputs silence. Notes that arrive while there is nothing to deliver them to are counted in `dropped_events()`.
- **Retiring.** Replaced plans, routings, songs, taps, replaced sample maps and removed devices are handed back through a retire queue and dropped by `EngineHandle::collect_garbage` on the caller's thread. If the queue is full the item is parked and further control messages wait. Nothing is ever dropped on the audio thread.

### Hot edits

A persistent **device arena** holds the prepared devices; a **routing plan** (order, levels, slots, cable copies, delay lines) only references them by slot. `Topology` is the non-RT routing model, validated like `Graph`; `Topology::compile` produces a `RoutingPlan`; `EngineHandle::{insert_device, remove_device, submit_routing}` queue changes. Structural edits therefore never reset a device's state. The `Graph` / `RenderPlan` / `submit_plan` API still works: a plan swap exchanges the whole arena and routing in one control message.

### Multicore

[workers.rs](../crates/engine/src/workers.rs): a pool of `atomik-render-N` threads runs the devices of one dependency level alongside the audio thread. Ownership is handed off, not shared: the audio thread moves `Box<Node>`s into per-worker `rtrb` job queues and gets them back through done queues (no `unsafe`, no locks). Gathering inputs and scattering outputs always happen on the audio thread, in plan order, so the output is bit-identical for any worker count. The audio thread waits at a barrier by spinning (counted as telemetry); idle workers spin, then park. A level with a single device is never dispatched.

## 4. Threading model

| Thread | Runs | May allocate or block? |
|---|---|---|
| Audio callback (cpal, or the caller of `render_offline`) | `Engine::render`, the song player, audio rendering, the record tap copy | No |
| Engine workers `atomik-render-N` | `Device::process_stage` of one level | No |
| UI thread (winit, vello) | `AppCore`, `Shell`, views, `EngineHandle` calls, `compile`, applying worker results | Yes, but never waits for the audio thread |
| `atomik-streamer` | `StreamSource::read` (disk), fills lane rings | Yes (disk), isolated from the audio thread by the ring |
| `atomik-import`, `atomik-load` | decode, resample, hash, write, peaks, read-back | Yes |
| `atomik-record` | drains the record tap, writes WAV, cuts laps, stores assets | Yes |
| `atomik-browse` | file browser: folder listings, the tree's sub-folders, the recursive walk, favourite and tag places, the drives | Yes (disk) |
| `atomik-probe` | file browser: audio header reads (`probe_file`), visible rows first | Yes (disk) |
| `atomik-preview` | file browser: decodes the previewed file and fills the preview ring | Yes (disk) |
| `atomik-library-save` | file browser: writes `library.json` from the newest snapshot | Yes (disk) |
| MIDI callback (midir) | maps event times to frames, pushes live notes | Yes, then one wait-free push |

The engine is created as two halves by `new_engine(cfg)` or `new_engine_with_options(..)`:

| Half | Type | Runs on |
|---|---|---|
| Real-time (RT) | `Engine` | the audio thread |
| Non-real-time | `EngineHandle`, `Graph`, `Topology`, the compile functions | any other thread |

They share only wait-free single-producer/single-consumer ring buffers (`rtrb`), allocated in `new_engine`, and a few atomics:

| Queue | Direction | Carries | Capacity |
|---|---|---|---|
| control | handle → engine | inserts, removals, routings, plans, timed params, tempo, song snapshots, transport, the record tap, device sample maps, `PreviewStart` and `PreviewStop` | 1 024 |
| retire | engine → handle | replaced plans, routings, songs, taps, sample maps, preview streams (`Retired::Preview`) | 64 (+ 1 parked) |
| removed devices | engine → handle | devices taken out of the arena | the arena size |
| params | handle → engine | `(device, param, plain)` | 4 096 |
| notes | handle → engine | `ScheduledNote` | 4 096 |
| live notes | MIDI thread → engine | live note events | 4 096 |
| stream requests | engine → streamer | `StreamRequest` | 256 |
| record ring | engine → writer | records of `u32` words | 4 s of input |
| preview ring | decoder → engine | interleaved stereo `f32` frames of the file being previewed (one ring per preview) | `PREVIEW_RING_FRAMES` = 65 536 frames |
| atomics | engine → everyone | dropped events, stream underruns, meters, latencies, the transport state (a seqlock cell) | – |

A full queue makes the handle method return `EngineError::QueueFull`; the engine never waits. Live audio adds `atomik-audio-io`: the callback publishes `(engine host frame, instant)` through a `FrameClock` (so MIDI can be mapped to an exact frame) and counts xruns and DSP load. cpal has no duplex stream, so captured samples reach the render callback through a wait-free ring.

## 5. The engine's console features

[crates/engine/src/console.rs](../crates/engine/src/console.rs), with the devices `atomik.channel` and `atomik.master`.

- **Stages.** A device may declare stages (`DeviceDescriptor::stages`, the stage of each socket). Insert and FX-return loops such as `channel.insert_send → effect → channel.insert_return` are device-level cycles, which HI-3 would reject. With stages the cycle check, render order, worker levels and delay compensation use (device, stage) nodes, with an implicit edge from stage `s` to `s + 1`. `Device::process_stage(stage, ctx)` defaults to `process` for stage 0.
- **Summing inputs.** A socket with `Direction::SummingInput` accepts many cables. Contributions are summed as a left fold in ascending source-endpoint order, fixed at routing compile, so the sum is bit-identical for any block size and worker count.
- **Plugin delay compensation (PDC).** At routing compile, in topological order, a device's output latency is the maximum over its inputs plus its own `latency_frames()`. Each cable into an Audio or Cv summing input is delayed by `max_in − lat_in`. Delay lines are allocated at compile, sized exactly, owned by the routing plan and dropped off the RT thread; a routing swap keeps the line of a cable whose delay did not change. If a delay would exceed 10 s, compensation is disabled for the plan and `PdcReport::limit_exceeded` says so. `set_compensation(false)` makes every delay 0.
- **Meters.** `Meters` is a fixed bank of atomics. After each batch the engine publishes peak and RMS per metered endpoint; the UI reads them once per frame.
- **Device meter values.** A device that answers `Device::has_meter_values()` with true when it is inserted gets `Device::meter_values(&self, out)` called by the audio thread once per batch, after the routing ran (every node is home), in ascending device id order. It writes up to `MAX_METER_VALUES` (32) latest values (gain reduction, loudness, band energies; peak-hold is the device's business). The engine stores them as f32 bits in the arena slot's bank inside `Meters` with a count, an owner id and a publish sequence that only grows; any other device costs one bool test per batch. The UI reads with `EngineHandle::device_meter_values(id, out)` or `Meters::device_values` (`AppCore::device_meter_values(key, out)`), getting `(count, seq)`; an unchanged `seq` means no news. A removed device (or a swapped plan) clears its slot, and a reader only gets values from the slot whose owner is the id it asked for, so a reused slot never shows old values.
- **Model and app.** The model keeps the console (`Console`, channels bound to rack devices, master, 8 returns); every instrument gets a channel automatically. Solo is additive and returns are solo-safe; the app sets `internal.solo_silence` on the engine only.

### Output buses (model)

[crates/model/src/console_bus.rs](../crates/model/src/console_bus.rs), with the device type `atomik.bus` (`console::BUS_TYPE`; the model never depends on the device crate). `is_console_type` is true for channel, bus and master, so a bus is left out of the device browser, cannot be copied, pasted, a channel source, a return or insert effect, or sit inside a container, and is excluded like a channel wherever console devices are skipped (sidechain sources, clipboard).

- **A bus is a strip.** `Console.buses: Vec<ConsoleBus { bus, name }>` lists the bus devices in console order (between the channels and the master in the console view). A bus has the channel's params and sockets except `in_l/in_r`, which become the summing input `bus_l`/`bus_r`. Invariants (loader and commands): every entry is an existing `atomik.bus` device listed once, with a trimmed, non-empty name of at most 32 characters, unique ignoring case (the device carries the same name), and buses exist only while there is a master. Project format 12 writes `"console"."buses": [{"bus", "name"}]` only when there are buses.
- **Routing is cables.** A strip's `out_l/out_r` go to one destination (`OutputDest`): `Master`, `Bus(key)` (cables to that bus's `bus_l/bus_r`) or `AudioIo(n)` (`out_l` to `interface:out_{2n-1}` and `out_r` to `out_{2n}`; pair 1 is outputs 1+2). Interface outputs take one cable, so a pair has one source; the master already owns 1+2. The sends of channels and buses always go to the master's `send_bus{k}`. `link_kind` classifies channel to master (`ChannelOut`), channel to bus (`ChannelToBus`), bus to master (`BusOut`), bus to bus (`BusToBus`) and the sends (`ChannelSend`, `BusSend`) as console links, hidden in the rack; Audio I/O cables are ordinary cables. `output_dest` reads `Master`, `Bus`, `AudioIo`, or `Direct`/`Mixed`/`None` as before; a channel hand-cabled to a free interface pair now reads `AudioIo` instead of `Direct`.
- **Commands** (`ConsoleCommand`, each one undo step, planned on a scratch copy): `CreateBus { name, dest }` (the device goes after the last bus, else at the end of the rack; its key is `console::new_bus_key(doc)` computed before; sends cabled to the master; the master is created when missing), `RenameBus`, `DeleteBus`, `ReorderBus`, `SetOutput { strip, dest }` (replaces every cable leaving the strip's `out_l/out_r`; refuses a loop, a bus that is not a bus, an Audio I/O pair beyond `output_channels` or already fed, and `Direct`/`Mixed`/`None`) and `RouteToNewBus { strips, name }` (a new bus on the master and the strips routed to it). Deleting a bus moves each feeder cable to the bus's own destination: the master, a bus, or its Audio I/O pair when it has exactly one feeder (a pair takes one cable), the master otherwise. `Command::RemoveDevice` and the workflow removal of a bus device are `DeleteBus`; the generic `Command::Rename` of a bus device is `RenameBus`. A bus has the channel's insert chain (`SetInsert`, `MoveInsert`, `CreateEffect` on a selected bus). Console devices are not copied: duplicating or pasting an instrument gives the new channel the master as output, whatever the original channel did, and a bus loses a feeder cleanly when its channel or instrument is removed.
- **Solo.** `RackDoc::solo_silence` returns the channels in console order, then the buses. With no solo nothing is silenced; otherwise a strip stays audible when it is soloed, when it is on the path of a soloed strip to the master or an Audio I/O pair, or when it feeds a soloed bus, both transitively; the siblings feeding a bus that is only on a soloed channel's path stay silenced. The app pushes `internal.solo_silence` to each strip by its own device type.

### Output buses (console, rack and app)

- **Model helper.** `console::output_options(doc, strip)` lists the destinations a strip's selector offers (master, each bus except the strip itself, every Audio I/O pair up to the format maximum), each with an `OutputAvail`: `Available` holds exactly when `SetOutput` would accept it, else `Loop`, `InUse` (a pair already fed by another source; pair 1 is the master's) or `BeyondOutputs`. A generic `AddDevice` of `atomik.bus` is refused: a bus is made by `CreateBus` or `RouteToNewBus` only.
- **Console strips.** `ConsoleView` holds the channel strips first, then the bus strips (`console.buses` order), all drawn by the same layout and painter (the bus descriptor has the channel's params, so `strip_layout` gives the same controls); the "add channel" placeholder keeps its place after the last channel, which puts a one-slot gap between the two groups, and a bus strip sits on a faintly tinted background with the caption `BUS n` and its name on the plate. Reordering a name plate by drag stays inside its group (`MoveChannel` among channels, `ReorderBus` among buses). A click on a plate selects the strip (Ctrl/Cmd toggles, Shift selects the range); the selection is view state, outlined on the plate, and what Ctrl/Cmd+G uses when the console has the focus. Mute, solo and the meters work as on a channel: the view's silenced flag comes from `RackDoc::solo_silence`, so a bus on a soloed channel's path and the feeders of a soloed bus read as audible.
- **Output selector.** Every strip has a slim selector row (`console_layout::OUT_H`) above its name plate; the master's reads `MAIN 1+2` in the same place so the faders line up. A click opens a menu: Master, each bus by name (loops left out), the Audio I/O pairs (greyed with the reason: `(the master)`, `(in use by <strip>)`, and one row `Audio I/O 5+6 and up: raise Outputs in Audio settings` for the pairs beyond `output_channels`) and `New bus...`, which sends `RouteToNewBus` with `default_bus_name()`. The menu marks the current destination, and a long one scrolls with the wheel. The selector label reads `Master`, `Bus <name>`, `Audio I/O 3+4`, `Custom` (hand-cabled), `Mixed` or `none`.
- **Rename and menu.** A double-click on a bus name edits it in place (the console is a text owner then: `ConsoleView::is_text_owner`, the shell puts `Text` on the context stack); Enter or a click elsewhere sends `RenameBus`, Esc cancels, at most 32 characters. A refusal (empty or duplicate name) is shown in the toolbar (`ConsoleView::notify_rejected`, cleared by the next click) and in the rack, like any rejected command. The right-click menu of a bus plate is Rename and Delete bus; a channel plate still removes the channel on right-click.
- **Route to new output bus.** `mixer.route_to_new_bus` (Ctrl/Cmd+G, Mixer menu): `AppCore::strips_to_route` takes the console's selection when the console has the focus and it is not empty, else the rack's selection (a channel or bus device is itself, an instrument is its channel), and `route_selection_to_new_bus` applies one `RouteToNewBus` named `Bus n`, then selects the new bus in the console. With nothing selected it says so instead.
- **Rack.** A bus is a console device like a channel: it is shown or hidden with "Show Console Devices in Rack", its cables are console links hidden unless "Show Console Links" is on, and its panel is the generic panel of its descriptor (the channel's controls, `bus_l/bus_r` as the summing input). The output display on the plate reads `Output: Master`, `Output: Bus <name>` or `Output: Audio I/O 3+4`; only a hand-cabled output that is none of these (`Direct`, `Mixed`) keeps the warning colour and the "Leaves the master" tooltip.
- **Meters.** The topology meters the `out_l`, `out_r` and `gr_cv_out` of every bus like a channel's (`CHANNEL_METER_SOCKETS`), so the console draws bus meters, gain reduction and latency readouts.

## 6. Audio tracks and the sample pool

### Files and the bundle: `atomik-audio-file`

Nothing in this crate runs on the audio thread. Every function may allocate and block on disk.

- **Decode** (`decode_file`, `decode_bytes`): WAV, AIFF, FLAC, MP3 and OGG through symphonia. A decoder panic becomes an error. Lossless sources must decode completely.
- **Resample** (`resample`): a fixed-parameter rubato sinc resampler with an exact alignment correction, so the result never depends on the caller. Used on import when the file's rate differs from the session rate.
- **Hash and ids** (`content_hash`, `is_valid_hash`): a SHA-256 over a canonical encoding of the decoded audio. The id is 64 lowercase hex digits and is checked everywhere it is used as a file name.
- **Peaks** (`PeakPyramid`): min/max per bucket at 256, 1 024, 4 096 and 16 384 frames, with a compact cache format.
- **`Bundle`**: the project folder. `Audio/<hash>.wav` (32-bit float), `Audio/.peaks/<hash>.peaks`. `import`, `add_recording`, `load`, `stream_reader` (`WavStreamReader`, seekable), `copy_bundle`, `orphans` and `remove_orphans`. Every file is written to `<name>.tmp~`, fsynced and renamed. `save_text_atomic` does the same for the project file.

### The model

`RackDoc::assets` is the sample pool (`AssetMeta`: channels, rate, frames, original name), keyed by id. `RackDoc::input_channels` is the number of host inputs (`interface:in_1..N`). An audio track is a track on an `atomik.audio-track` device whose lane 0 is `LaneKind::Audio`; its clips are `ClipContent::Audio(AudioClipContent)` with the asset id, source offset in frames, gain in dB, fades in frames and a fade curve. Clip start and length stay in ticks; audio is not stretched. `flatten_audio` turns a track into non-overlapping regions (later clips win; fades are measured inside the original clip).

### The engine side

- **Assets and regions** ([audio.rs](../crates/engine/src/audio.rs)): `SongAsset::Memory` (planar `f32`, shared) or `SongAsset::Stream`. A `SongAudioRegion` is a song-frame start, a source offset, a length, a linear gain and the fade data. For region frame `i` the output is `asset[offset + i] × (gain × fade(i))`, cut at the region end and the asset end. Mono plays on both channels, and for more than two channels the first two are played. Equal-power fades use `sin_quarter`, a polynomial that calls no libm function, so every platform rounds the same (HI-2).
- **Rendering.** `Renderer::segment` renders each batch segment into a preallocated stereo pair per track, at its batch offset, so loop wraps and locates are sample-accurate. `publish_audio` hands the pair to the track's device node, and `ProcessContext::playback` gives it to `Device::process`.
- **Streaming** ([stream.rs](../crates/engine/src/stream.rs)): see 2.5. The ring carries the track's streamed regions' samples in playback order, tagged by playback index and epoch, so loop wraps need no refill. `EngineHandle::{stream_underruns, stream_primed}` report the state; the app delays Play until the lanes are primed. Offline bounces use `Memory` assets only.
- **Record tap** ([record.rs](../crates/engine/src/record.rs)): see 2.6. `EngineHandle::record_tap(channels, capacity)` allocates the ring off the RT thread and queues the tap; `RecordTap::drain` returns only runs that are contiguous in engine frames, so a start tag is always exact; an overflow is counted in frames and never blocks.
- **The device** `atomik.audio-track` ([audio_track.rs](../crates/devices/src/audio_track.rs)): `out = playback + input × monitor_gain`. `monitor` is off, auto or on; with auto the app's `internal.monitor_live` (the arm flag) decides. A change is a 5 ms crossfade. It has one stage and no latency.

### The app: workers and rules

[crates/app](../crates/app): `AppCore` (no window, no GPU) owns the document, the registry, the views and the engine sink; `Shell` is everything inside the window; `platform/` is winit, the GPU and the native menu. Audio adds:

- [`app_core_audio.rs`](../crates/app/src/app_core_audio.rs): bundle rules, import, the asset cache, Save and Save As.
- [`audio_import.rs`](../crates/app/src/audio_import.rs): the import and load workers (message passing only).
- [`stream_source.rs`](../crates/app/src/stream_source.rs): the 64 MiB streaming threshold and the engine's `StreamSource` over a WAV reader (a read error plays as silence and is counted).
- [`audio_record.rs`](../crates/app/src/audio_record.rs): the pure recording rules (compensation, laps, placement).
- [`audio_writer.rs`](../crates/app/src/audio_writer.rs) and [`app_core_rec_audio.rs`](../crates/app/src/app_core_rec_audio.rs): the writer thread and the glue that follows the transport.
- The bundle layout and Save rules are shared with the bounce in [crates/render/src/bundle.rs](../crates/render/src/bundle.rs).

## 6a. Sample devices

The sampler `atomik.sampler` ([DEVICES.md](DEVICES.md#sampler-atomiksampler-instrument)) is the first device that plays shared sample data. The path from a dropped file to a sounding voice:

- **Sample maps** ([device-sdk/src/samples.rs](../crates/device-sdk/src/samples.rs)). A `SampleMap` is a list of `Arc<SampleBuffer>` (planar, immutable, at the session rate) and a list of `Zone`s. `SampleMap::new` validates every zone (ranges, frames inside the buffer, start < end, loop fields inside start..end when looping, crossfade fits), so a device never checks again. Types that take samples are registered with `Registry::register_with_samples` and answer `Registry::takes_samples`; the model and the app ask the registry, not a device list.
- **Swap and draining.** `Device::swap_samples(map) -> Option<SampleMapRef>` is RT-safe and allocation-free. The sampler holds at most two maps, `current` and `draining`, and never drops one: it hands one back. A voice whose zone index exists in the new map with a pointer-equal buffer moves to it and keeps its position; every other voice keeps playing from the old map (now draining) with a 5 ms fade-out. A second swap while voices still drain cuts them and returns the draining map; a stale draining map comes back at the next swap. Exactly one map (or none) is returned per call.
- **Engine.** `EngineHandle::set_device_samples` checks the id against the mirror (unknown ids are rejected on the handle side), then queues `ControlOp::Samples`, applied at a batch boundary in queue order, so insert then samples works. The audio thread calls `swap_samples` and queues the returned map as `Retired::Samples`; `collect_garbage` drops it off the audio thread. A removed device's maps leave with the device through the same retire path. Hot edits can carry samples (`HotEdit::Samples`); offline and patch builds call `Graph::set_device_samples` before `compile`, which drops the returned map on the non-RT thread.
- **Model** ([model/src/zones.rs](../crates/model/src/zones.rs)). `RackDevice::zones` is a list of `ZoneDoc` (the SDK `Zone` with a pool asset id instead of a buffer index; empty and not serialised for every other device). `Command::SetZones { device, zones, merge: Option<u64> }` replaces the whole list in one undo step and merges consecutive drags with the same id on the same device (`MergeKey::Zones`). It is validated with the SDK's own `SampleMap::new` over throwaway data-less buffers, so the model and the engine cannot disagree, and each asset must be in the pool with frames inside its length. `SyncOp::ZonesChanged` tells the app. Zone assets count in `referenced_assets`, including the undo and redo history. Project format v4 stores `zones` inside the device object; v1 to v3 still load, and zones need version 4. `auto_map` and `parse_note_name` turn dropped files into zones (C4 = 60; a note name in the stem sets the root and neighbouring roots split the keyboard halfway; otherwise one key each from C4 or the drop key, in name order).
- **App** ([app_core_samples.rs](../crates/app/src/app_core_samples.rs)). `AppCore` builds each sampler's map from the asset cache with the shared builder `atomik_render::samples::build_sample_map` and sends it through `EngineSink::set_device_samples`: on every `ZonesChanged`, right after a sampler is inserted (so after every engine restart, in order), and when an asset finishes loading. Sampler assets are always in RAM: a memory asset of an audio track shares its sample data and one `Arc<SampleBuffer>` per asset is kept (so a zone edit keeps voices on the same buffers); an asset that is only streamed is loaded fully by a worker. Zones whose audio is missing or not loaded yet are left out of the map and play silence, and stay in the document. `UiAction::ImportSamples` runs the import worker and applies the `RegisterAsset`s and one `SetZones` as a single undo step. `--stress-sampler` adds 4 samplers of 32 voices to the stress song.
- **Editor pane.** `Pane::SampleEditor` shows `SampleEditorView` ([ui/src/sample_editor.rs](../crates/ui/src/sample_editor.rs)) in place of the arrangement. Opened by `UiAction::OpenSampleEditor` (double-click on the panel or its Edit button), closed by `CloseSampleEditor` (button, Esc, or when the sampler is removed). Auditions send `UiAction::AuditionVelocity` (7-bit velocity from the click height; the core sends `velocity / 127` and a matching note-off); `LoadSamplesDialog` asks the shell for the file dialog.
- **Render.** The bounce builds the same maps from the bundle (always memory) with the shared builder and installs them with `Graph::set_device_samples` before compile ([render/src/project.rs](../crates/render/src/project.rs), [build.rs](../crates/render/src/build.rs)). A missing zone asset is a bounce error that names it; the live app plays silence instead. Live and bounce are bit-identical once the live transport's one-batch (64 frame) start delay is removed.

## 6b. Drum machine and loop slicer

Both devices sit on the 4b-2a sample path (section 6a): zones, `SetZones`, the sample map swap and the shared map builder are unchanged. What they add:

- **Pads are zones** ([model/src/zones.rs](../crates/model/src/zones.rs)). `atomik.drum-machine` has 16 pads on the fixed keys 36 to 51 (pad *n* = key 35 + *n*). A pad's sound is the zones with `key_lo == key_hi ==` its key, so velocity layers need no new data; zones on other keys are ignored. The helpers `pad_key`, `pad_of_key`, `pad_zones`, `with_pad_files` (one file at full velocity, several split evenly by velocity in name order) and `fill_empty_pads` build the zone lists; the app applies each as one `SetZones`. A pad plays at most 8 zones. Choke groups (a hit fades the other pads of its group over 2 ms, group 0 never chokes), per-pad monophonic retrigger (the previous hit fades over 2 ms), 32 voices with oldest-first stealing, and gate or one-shot per pad are inside the device ([drum_machine.rs](../crates/devices/src/drum_machine.rs)).
- **Individual outputs and several channels per source.** The drum machine has `pad1_out_l` to `pad16_out_r` besides `out_l`/`out_r` (35 audio sockets), global `level_cv_in` and `pitch_cv_in`, and a `padN_gate_cv_in` and `padN_gate_cv_out` per pad (69 sockets in all). A pad whose output is connected on either side plays only there; the soft limiter and master level apply to the main mix only. `ConsoleCommand::AddChannelFor { source, out_l, out_r, name }` ([model/src/console_cmd.rs](../crates/model/src/console_cmd.rs)) makes a console channel fed by chosen audio outputs of a source, in one undo step. It is validated: both sockets must be audio outputs of the source and not already cabled, and the source must not be a console device or sit on a return. `ConsoleChannel::source` lets one source feed several channels; solo, removal of the source (all its channels go with it, and undo brings them back) and save and load handle that. The rack's TO CH button on a pad uses it and names the channel "Drum machine Pad N".
- **Insert chains.** `ConsoleCommand::SetInsert { channel, slot, effect }` and `MoveInsert { channel, from, to }` ([model/src/console_insert.rs](../crates/model/src/console_insert.rs)) put up to four stereo effects on a channel's or the master's insert loop, wired in order `insert_send → fx1 → … → insert_return`. The chain is derived from cables (`insert_chain`), so nothing new is saved and the project format is unchanged; a hand-cabled loop of the same shape reads back as a chain. `InsertEffect::New { type_id }` adds a device right after the previous stage, `Existing(key)` takes a rack effect; replacing or removing a slot drops its cables but leaves the device in the rack; an empty chain leaves the insert unpatched. Each edit is one undo step, validated on a scratch copy (effect kind and stereo sockets, no cycle, not a return effect, a channel source or a member of another chain). Bypass is the existing `insert.bypass` param. The console strip's INSERTS section (and the master's bus column) shows four slot rows: a filled slot (name plus x) selects the effect in the rack or removes it, the first empty slot opens the add menu (new effect types, then free rack effects).
- **Step grid and swing in flatten.** A note clip may carry `StepGrid { resolution (1/8, 1/16, 1/32), steps 16..=64, swing 0..=75 % }` (`Clip::grid`, `SongCommand::SetClipGrid`, merged for swing drags). Swing is applied when the clip is flattened for the engine ([song/flatten.rs](../crates/model/src/song/flatten.rs)): a note in an odd step, counted from the clip's content start after the offset, moves later by `(swing x step + 100) / 200` ticks (integer arithmetic, so live and bounce agree to the bit); its length stays; every loop pass swings alike; a note pushed past the clip or loop end is dropped. The document's notes are never changed by swing.
- **`Command::Batch`** accepts `Connect`, `Disconnect`, `SetClipGrid`, `SetClipGeometry`, `AddTrack`, `AddClip`, `SetParam` and `SetZones`. The commands are validated in order against a scratch copy, the whole batch is rejected if one fails, it is one undo step, and each kind of `SyncOp` is reported once (one `ZonesChanged` per device). A merge id inside a batch is ignored. The step editor uses it for grid plus length, "New pattern" for track plus clip, the audio track selector for cables, and the loop load for `loop.beats` plus slices.
- **Reverse in the shared playhead.** `Zone::reverse` / `ZoneDoc::reverse` mark a reversed zone. `PlayRegion::reversed` has no loop; its `Playhead` starts at `end - 1`, steps down to `start` and fades out at `start`. The sampler, the drum machine and the slicer all use it, so there is one rule ([dsp/src/sample_read.rs](../crates/dsp/src/sample_read.rs)).
- **Onset detection** ([dsp/src/onset.rs](../crates/dsp/src/onset.rs)). `detect_onsets(channels, rate, sensitivity)` is pure, deterministic and allocating, so it runs only on a worker: a mono sum, RMS energy flux with a window of 1024 and a hop of 256 frames at 48 kHz, an adaptive threshold from the sensitivity (only IEEE arithmetic and `sqrt`), localisation back to the foot of the attack (at most 5 ms) and a 30 ms minimum gap. More sensitivity never gives fewer onsets.
- **Slicing helpers** ([model/src/slices.rs](../crates/model/src/slices.rs)). `atomik.loop-slicer` plays slice *n* on key 23 + *n* (24..=87, at most 64 slices) as a zone over the loop asset. `slices_from_markers` normalises markers (sorted, first at 0, at least 1 ms apart, at most 64) and keeps the per-slice fields (gain, pan, transpose, tune, reverse) by slice index; a new slice copies the last previous slice's fields. `grid_markers` is exact integer arithmetic and reduces the divisions when beats times divisions exceed 64. `to_track_notes` writes one note per slice at `round_half_up(start x beats x PPQ / frames)` ticks (u128 arithmetic) with the length up to the next slice, and the clip is `loop.beats` long. `default_loop_beats` rounds the loop length at the song tempo to whole beats.
- **App** ([app_core_drums.rs](../crates/app/src/app_core_drums.rs), [app_core_slicer.rs](../crates/app/src/app_core_slicer.rs)). Importing on a drum machine uses the pad rules above; on a slicer only the first file is used, and a worker runs onset detection at the current sensitivity, so the UI thread never analyses audio. The result is applied as one `Batch` of `SetParam loop.beats` and `SetZones` (dropped if the document generation changed). `SliceLoop` (transients on a worker, or an even grid) ends in one `SetZones` that keeps the per-slice fields; `SlicesToTrack` writes the clip as one undo step (replacing the selected clip of the slicer, else adding one at the bar-snapped playhead, with `AddTrack` in a `Batch` if needed). The demos are `examples/projects/drum-demo` and `slicer-demo`; `--stress-drums` and `--stress-slicer` add 4 devices with dense patterns to the stress song.
- **Panes.** Three panes replace the arrangement and exclude each other (section 7): the sample editor, the step editor (`Pane::StepEditor`) and the slice editor (`Pane::SliceEditor`); each closes when its device or clip goes away.
- **Project format v6.** v5 added the clip `grid` (only when present); v6 adds `reverse` to every zone (required in v6, rejected before). Saving always writes v6; v1 to v5 still load.

## 6c. Effects

Six original Effect devices in `atomik-devices`, each stereo with the sockets `in_l`, `in_r`, `out_l`, `out_r` (the compressor adds `sc_in_l`/`sc_in_r` and a gain-reduction CV out). Their DSP building blocks live in `atomik-dsp` (`fdn`, `oversample`, the existing `biquad`, `dynamics`, `lfo`). Every effect is allocation-free in `process`, deterministic (bit-identical across host blocks and worker counts) and finite for any params; details and parameter tables are in [DEVICES.md](DEVICES.md).

| Device | Notes |
|---|---|
| `atomik.reverb` | 8-line feedback delay network with room, hall and plate settings, seeded parabolic LFO modulation, freeze, latency 0. |
| `atomik.compressor` | Peak or RMS detector, soft knee, auto release, key filters, sidechain input, look-ahead 0 to 5 ms reported as latency. |
| `atomik.eq` | Six bands (cut slopes 12/24/48 dB per octave), coarse band levels published for the analyser. |
| `atomik.distortion` | Five curves, off/2x/4x halfband oversampling; the oversampler's latency is reported and the dry path is delayed to match. |
| `atomik.modulation` | Chorus, flanger, phaser with tempo sync from the transport. |
| `atomik.mastering` | 3-band multiband, mid/side width, look-ahead true-peak limiter (4x detector), BS.1770 / R128 loudness and true-peak meter. |

- **Latency.** A device's `latency_frames()` may follow a param (compressor look-ahead, distortion oversampling, mastering). The engine's PDC (section 2.4) recompiles when it changes and the changed cables' delay lines restart, which is audible once at the change (known limitation).
- **Meters.** Reduction, levels, loudness and EQ band energies reach the UI through the device meter values of section 5; `RackView::set_device_meter_values` feeds the panels once per frame.
- **Sidechain helper.** The UI emits one `Command::Batch` (disconnect the old source, connect the new one, set `sc_enable`) so the helper is one undo step.
- **Insert chains** are described in section 6b (`ConsoleCommand::SetInsert`, `MoveInsert`); the example project is `examples/projects/fx-demo`, and `--stress-fx` is the app's stress project for them. The factory effect `atomik.character`) has the example `examples/projects/character-demo` and `--stress-character`; its two latency classes make the engine's latency epoch move in the middle of a song, so a bounce follows the epoch like the live app does (`render::plugin_pass::render_song_following_latency`, 64-frame batches, routing recompiled after the batch).

## 6d. Step sequencer and arpeggiator

Two original note devices (`DeviceKind::Utility`, listed together as "Players" in the browser) that take notes in and send notes out over an ordinary Notes cable, plus gate, pitch, velocity and trigger CV. Details, socket and param tables are in [DEVICES.md](DEVICES.md).

- **Transport position for devices.** `TimeInfo` carries `tick` (the transport position at the first frame of the batch, fractional), `ticks_per_frame` (constant inside a batch) and `loop_wrap` (offset and target tick of a wrap strictly inside the batch, at most one, only with a song). `Player::run` returns a `BatchTime` and `run_batch` copies it into the `TimeInfo` of every device. Without a song the tick is a free-running accumulator at the engine tempo. A wrap exactly on a batch boundary is reported as a tick jump only. A device never reads wall time.
- **Note clock** ([devices/src/note_clock.rs](../crates/devices/src/note_clock.rs)). Both players share one clock. Step `k` of resolution `s` ticks starts at `k x s` plus, for odd `k`, the integer swing shift `(swing x s + 100) / 200`; its On is due at the first frame `ceil((start - batch tick) / ticks_per_frame)` (a 1e-6 frame tolerance), so steps are derived from the tick every batch and never drift. A `JumpTracker` flags a locate, a start, a stop or a clock-source change (a tempo change inside a batch is tolerated in proportion to the change of `ticks_per_frame`); at a jump every sounding note is closed and the step counter is recomputed from the new tick. Offs that fall into a later batch wait in a fixed 64-slot `PendingOffs` table that stores absolute ticks. `NoteCore` writes notes and CV (gate, pitch `(key - 60) / 24` clamped, velocity, a 1 ms trigger) and keeps event offsets non-decreasing.
- **Pattern data hand-over.** Like sample maps: `Registry::register_with_player_data` marks the type, `Device::swap_player_data` is RT-safe and hands the old `Arc<PlayerData>` back, the engine queues `ControlOp::PlayerData` (applied at a batch boundary in queue order, so insert, then data, then routing) and retires the returned value through the garbage path (`Retired::PlayerData`, `HotEdit::PlayerData` offline). A swap never cuts a sounding note: its end is already scheduled.
- **Step sequencer** ([devices/src/step_sequencer.rs](../crates/devices/src/step_sequencer.rs)). Up to 8 patterns of 1 to 64 steps; per step on, key, velocity, gate length, probability and tie; per pattern a resolution (seven values) and a swing. Step index = global step number mod length, so locates and loops land in phase. Transport-synced only; with no data it plays nothing. Pattern switch `now` or at the pattern end, transpose, follow (a held key on `notes_in` transposes), mute, velocity and gate scale.
- **Arpeggiator** ([devices/src/arpeggiator.rs](../crates/devices/src/arpeggiator.rs)). Held keys in `notes_in`; modes up, down, up-down (no repeated ends), random, as-played and chord; octave range 1 to 4; seven tempo-synced rates; gate, swing, hold, input or fixed velocity. With `run = always` and the transport stopped it uses an internal clock that starts at the playhead tick and advances at the current tempo, so a keyboard can be arpeggiated with the song stopped.
- **Determinism.** No running RNG: a probability test or an arpeggiator random pick is `hash64(device seed ^ random.seed, global step number, slot)`, so a bounce, a live run, a locate and a second loop pass give the same result from any start position and any block size.
- **Model** ([model/src/steps.rs](../crates/model/src/steps.rs), [steps_cmd.rs](../crates/model/src/steps_cmd.rs)). `RackDevice::steps` holds a `StepSeqDoc` (1 to 8 `PatternDoc`s, each with always 64 steps so a longer length keeps old data). Commands `SetPattern` (drags merge), `AddPattern`, `RemovePattern` (lowers the `pattern` param in the same undo step), `DuplicatePattern`; all four are accepted by `Batch`. `SyncOp::PatternsChanged` covers edit, undo and redo. `to_player_data` and `player_data_for(device, registry)` build the engine value; the model refuses `steps` on devices that take no pattern data. Project format v7 writes `steps` only when present; v1 to v6 load.
- **UI** ([ui/src/seq_panel.rs](../crates/ui/src/seq_panel.rs), [arp_panel.rs](../crates/ui/src/arp_panel.rs), [seq_editor.rs](../crates/ui/src/seq_editor.rs)). Hand-made 2 U panels (8 pattern slots, preview and Edit for the sequencer; mode and rate buttons and a live held-keys display for the arpeggiator) and the grid editor pane `Pane::SeqEditor` (note lane plus velocity, gate and probability bar lanes, tie toggles, length, resolution and swing, playing-step cursor, audition). Both players publish meter values (sequencer: pattern, step, running; arpeggiator: held count and the next 8 keys) that the app feeds to the panels and the editor.
- **App and render** ([app/src/app_core_players.rs](../crates/app/src/app_core_players.rs), [render/src/project.rs](../crates/render/src/project.rs)). The app sends each sequencer's data right after its insert and on every `PatternsChanged` (one swap per edit, undo or redo); the renderer installs the same `player_data_for` maps before compile, so a bounce equals live playback. `examples/projects/player-demo` and `--stress-players` (4 chains of sequencer, arpeggiator and synth) are the demo and the stress load.

## 6e. The container device

`atomik.container` is a device whose inside is another rack: its own devices and cables, eight macro knobs that drive inner params, and note splits that route incoming notes by key and velocity to inner instruments. It has stereo audio in and out and a notes in, and it is saved inside the project. The decisive design choice is **flattening**: the engine has no container concept. A pure model function turns the tree into the flat device and cable lists the engine already understands, so PDC, multicore levels, summing order, seeds and hot edits work on the exact flat graph unchanged.

- **Document** ([model/src/container.rs](../crates/model/src/container.rs)). `RackDevice::inner: Option<Box<ContainerDoc>>`, only on devices of `DeviceKind::Container`. `ContainerDoc { devices, cables, macros: [MacroDoc; 8], splits: Vec<NoteSplit> }`; inner cables and splits use local keys, and the reserved key `boundary` names the inside edge (outputs `in_l`, `in_r`; inputs `out_l`, `out_r`). Limits: nesting depth 3, 32 devices per container, 256 inner devices per project, 8 splits, 32 targets per macro and 128 per container; no console devices, audio tracks, the interface or the split device inside.
- **Path keys.** An inner device is addressed everywhere by the keys from the top joined with `/` (`layer/synth`); `/` and `~` are not valid in a user key, so a path never collides. `RackDoc::resolve` and `resolve_mut` walk the tree; `RackDoc::device` stays top-level only so a site that forgot the expansion fails loudly. Song tracks, console sources, returns and the interface cannot name an inner device. Commands ([container_cmd.rs](../crates/model/src/container_cmd.rs)): `ContainerCommand::{AddInner, SetSplits, SetMacro, RemoveMacroTarget, RenameMacro, DuplicateContainer}` plus path keys in the existing commands; each is one undo step, drags merge (ids from 7 x 2^40), and the new sync ops are `MacrosChanged` and `SplitsChanged`.
- **Expansion** ([model/src/expand.rs](../crates/model/src/expand.rs)). `RackDoc::expand(&Registry) -> ExpandedRack` gives the flat devices (path keys, macro-applied params, zones, steps), the spliced cables, the alias of a container to its `~split` device and the macro targets. Order: rack order, each container's slot taken by its `<container>/~split`, then its inner devices depth first; the engine id is the 1-based position in that list on load and bounce. Cables are spliced by tracing every flat input backward through boundaries and containers (a pass-through loop is caught by a hop limit and reported as a cycle); a boundary end with nothing behind it is a silent edge; a cable that would appear twice is rejected. A document without containers expands to itself. The cycle check of a cable runs on the expanded graph (Kahn over (device, stage)) only when the document has a container, so insert and return loops through containers are judged as the engine judges them.
- **Split device** ([devices/src/note_split.rs](../crates/devices/src/note_split.rs)). `atomik.note-split` is internal (`INTERNAL_TYPE_IDS`, never in the browser): one Notes input, eight Notes outputs, six params per slot (`sK.on`, key and velocity ranges, transpose). A Note-On goes to every enabled slot whose ranges contain it; each slot keeps a per-key route (and an owner table per output key) so the matching Off follows the same route even after a param change, a retrigger closes the old note first and `AllOff` clears every table. Allocation-free, latency 0.
- **Macros** (`macro_value` in expand.rs). `v = min + (max - min) x m`, clamped to the descriptor range, discrete and choice params rounded half up by comparison; only IEEE `+ - *`. A param is driven by one macro in the whole project; `SetParam` on a driven param is `MacroDriven`; an outer macro may drive an inner container's `macroN` (outermost first). Automation of `macroN` on a song lane expands (`expand_macro_lane`) into one lane per target with the points mapped by the same function, so it equals hand-made lanes on the targets bit for bit.
- **Format v8** ([model/src/container_io.rs](../crates/model/src/container_io.rs), [project.rs](../crates/model/src/project.rs)). `inner` is written after `steps` only when present, in the canonical form of the top level; v1 to v7 load; every violation is a load error naming its JSON path; a v1 to v7 device keyed `boundary` is renamed `boundary-N` with a warning.
- **App and render** ([app/src/app_core_containers.rs](../crates/app/src/app_core_containers.rs), [render/src/flat.rs](../crates/render/src/flat.rs), [render/src/project.rs](../crates/render/src/project.rs)). Everything that feeds the engine reads one `RackDoc::expand` per edit: `rebuild_engine` inserts the expanded devices in order, then one routing; `DeviceAdded(container)` inserts its split and inside, `DeviceRemoved(container)` removes every id with the `container/` prefix. Macro values and `~split` params are sent right after the insert and again on `MacrosChanged` and `SplitsChanged`, as deltas only (`macro_sent`, `split_sent`). `target_of` resolves a container to its split, so the keyboard, audition, the editor's preview and a song track reach the inner instruments through the splits. The bounce builds the patch from the expansion (inner devices get generated patch ids; the engine id is the position), so live equals bounce; `expanded_ids` replaces `rack_ids`. A lint test pins the few raw `doc.devices` uses.
- **UI** ([ui/src/container_panel.rs](../crates/ui/src/container_panel.rs), [breadcrumb.rs](../crates/ui/src/breadcrumb.rs), [container_editor.rs](../crates/ui/src/container_editor.rs), [rack/container_input.rs](../crates/ui/src/rack/container_input.rs)). A double-click or OPEN enters a container: the rack view works on a scope document (the container's devices and cables with local keys, boundary drawn as two pseudo-panels) and lifts what it emits to path keys and `ContainerCommand`s; a breadcrumb bar, Back, Esc and Backspace go up. The 2 U panel has OPEN, EDIT, TO CH and eight named macro knobs; a right-click on an inner control maps it to a macro, a mapped control is locked, and Ctrl/Cmd+D duplicates the selected container. `Pane::ContainerEditor` has a SPLITS tab (key by velocity map with draggable bars, audition) and a MACROS tab (name, value, targets with min and max).
- **Console.** A container has no channel at creation; TO CH adds one, and an effect container works in an insert chain or on a return (`console_insert` accepts `DeviceKind::Container`). Inner latency (a compressor look-ahead) is compensated by the existing PDC on the flat graph at summing inputs; parallel inner paths that meet in a plain input are not compensated, as at the rack level.
- **Tests as proof.** The expansion theorem (`render/tests/container_demo.rs`): the container bounce is bit-identical to a hand-built flat twin across host blocks and worker counts; `engine/tests/flat_container.rs` does the same for hand-built flat graphs with PDC and 264 devices; `app` tests prove live equals bounce through edits, undo, redo and an engine restart. Example: `examples/projects/container-demo`; stress: `--stress-containers`.

## 6f. Plugin hosting

Third-party CLAP and VST3 plugins are rack devices: instruments and effects that are cabled, automated, macro-mapped, saved and bounced like any built-in device. Both formats go through one machinery (the host crate, the manager, the device, the scanner, the model and the UI); a format is a backend behind `PluginBackend`. The user-facing behaviour is in [DEVICES.md](DEVICES.md#third-party-plugin-devices-clapid-and-vst3id). By default every plugin instance runs **in its own process** (the sandbox, below), so a plugin that crashes or hangs cannot take the app down; Settings > Plugins can switch back to running plugins inside the app process (applied at the next start). Scanning is always out of process.

- **Crates and the unsafe policy.** `atomik-plugin-host` (no `unsafe` except the audited `fpenv.rs`: the generic `PluginDevice`, the `PluginManager`, the slot and hand-shake, scan, cache, catalog, journal, settings), `atomik-plugin-clap` (the CLAP backend over `clack-host` and `clack-extensions` 0.2.0, pinned), `atomik-plugin-vst3` (the VST3 backend over the `vst3` crate 0.3.0, pinned, bindings generated from VST 3.8; the host layer is ours), the only two crates with plugin `unsafe` (every block with a `SAFETY:` comment), `atomik-plugin-scan` (the scanner child binary, both formats), and the in-repo test plugins under `crates/testplugins` (`core` holds the DSP shared by every test plugin, so a CLAP and a VST3 effect can be required to give the same bits; `clap-shell` is a raw `clap-sys` plugin shell and `vst3-shell` a plugin shell over the `vst3` crate's plugin-side helpers, so each host is tested against a plugin not built with its own library; `clap`, `vst3` and the `-bad`, `-hang`, `-crash`, `-leak` and `-variants` libraries of each format are cdylibs). `atomik-model` never names a plugin crate. `unsafe_code = "deny"` everywhere else; [plugin-host/tests/unsafe_policy.rs](../crates/plugin-host/tests/unsafe_policy.rs) pins the allowed places by name and requires a `SAFETY:` comment on every block.
- **One descriptor per plugin.** `descriptor_for(&PluginRef, &PluginLayout)` in `atomik-device-sdk::plugin` builds a `&'static DeviceDescriptor` once per distinct (plugin, layout) and **interns** it (a deliberate, bounded leak: at most 4 096 descriptors per process, 2 048 params each, pinned by tests). Type ids are `clap.<id>` and `vst3.<32 hex digits of the class id>` (the same text on every OS); sockets follow the rule `in_l, in_r, sc_in_l, sc_in_r, notes_in, out_l, out_r, notes_out`; params are `bypass` then `p<plugin id>` keys with the plugin's own plain value (CLAP value; VST3 normalised, stepped as index). `Registry::register_plugin` keeps plugin types in their own map; `Registry::create` of a plugin type builds the stand-in device, the real one comes from the manager.
- **The device (RT side).** [plugin-host/src/device.rs](../crates/plugin-host/src/device.rs): `PluginDevice` implements `Device` for every backend through the object-safe `PluginProcessor`. It calls the plugin with exactly **64 frames** per batch (so live, bounce and every host block feed it identical blocks, drains a fixed param table into coalesced events at the batch start, turns `NoteKind`s (now including pitch bend, CC, pressure and note expressions) into note and MIDI events with host note ids, passes the batch `TimeInfo` as the transport, writes the output through a 5 ms bypass crossfade to the dry main input, applies the sleep and skip rules (they depend only on batch content), sets flush-to-zero around `process`, and turns an error status, a panic or a non-finite output into FAILED (silence, or dry for effects). Nothing in this path allocates or locks (`assert_no_alloc` tests at host blocks 1, 64, 333, 480, 512 with workers 1, 2, 4 and a restart in the middle).
- **Lifecycle (the manager).** The winit thread is the plugin main thread. `PluginManager` owns each instance's main-thread half, moves only the audio processor half into the `PluginDevice`, and talks to it through a `PluginSlot` (atomics) and wait-free `rtrb` rings. A **restart** (sample rate, latency or param-table change, RELOAD) is a hand-shake: the manager requests a stop, the device answers silence or dry and hands the processor back at the next batch, the manager deactivates and activates again and sends it back; the device then re-sends every param the rack ever set. Dropping a device never destroys the plugin on the dropping thread: `Drop` posts to the **reaper queue**, and `poll` tears down on the main thread. An engine restart keeps the living instances (`retain`, then `reattach` at the new rate: nothing is created again). Plugin callbacks into the host only post to a bounded message ring that `poll` drains; a full ring drops and counts.
- **Latency and PDC.** The reported latency (clamped to 1 s) is an atomic on the slot; `Device::latency_frames` reads it and the engine's existing PDC does the rest. A plugin announces a change (CLAP `latency.changed`, VST3 `restartComponent(kLatencyChanged)`), the manager restarts it, the backend reads the latency again after the re-activation (the VST3 backend also after every `setActive` and every state restore), and the app recompiles the routing once the engine publishes it (the known single discontinuity of effect latency changes). The same loop runs in a bounce (see Render).
- **Scanner, cache, consent.** Plugins are off by default. `atomik-plugin-scan clap <path>` loads one file in a child process, activates every plugin once, and prints a JSON `ScanResult`; the app runs up to two children with a hard timeout (default 30 s, 5 to 300), kills a hang, and blacklists files that crash, hang, print garbage or are not plugins until they change or the user retries. `plugins.json` (atomic write, versioned, incremental rescan by size and mtime) feeds `PluginCatalog`, which registers descriptors **without loading any plugin file**. A project never carries a path: a device resolves only by (format, id) against that cache. A project that uses missing or disabled plugins opens with **stand-ins** that keep cables, channel, song track, automation, macro targets, pins and the state blob byte for byte, and RELOAD or a rescan swaps the real plugin in.
- **State and undo.** The plugin state is an opaque byte blob (`state.save` into a buffer), captured before every save, when the editor closes, a quiet second after `state.mark_dirty`, before an engine restart and before the device is removed; it lives in the document as `PluginDoc::state` through `PluginCommand::SyncState`, which is not an undo step. Caps: 16 MiB per plugin, 128 MiB per project. On restore the state goes first and the rack's saved params after. Edits made in the plugin's own window become `SetParam`s through a gesture merger (merge ids from 8 x 2^40, one gesture is one undo step, flagged so they are not echoed back to the plugin); a patch change inside the plugin is not undoable.
- **Format v9.** `plugin` is written after `inner`: format, id, name, vendor, version, `path_hint` (shown, never used), a compact `layout` (sockets and **only the used param rows**), base64 `state`, pins, run mode, powered. Params are saved sparsely. Canonical save, load, save is byte-identical; every violation names its JSON path; v1 to v8 load unchanged. A param key a newer plugin no longer has is a **dead key**: kept in params, lanes and macro targets, ignored at send time, never a load error.
- **Editor windows.** The core never touches a window: `PluginWindowRequest`s go to the platform layer, which creates one plain winit window per editor (no wgpu surface), hands the native handle (Win32, AppKit, Xcb, Xlib) to the backend for `gui.set_parent`, and forwards resize and close. Wayland has no embedding: the PARAMS pane (a searchable, module-grouped list of every param) is the fallback and the editor for plugins without a GUI.
- **Crash handling.** Sandboxed (the default), a plugin crash ends only its own process: the device turns CRASHED and RELOAD creates a new instance (see the sandbox below). In process, a native plugin crash takes the app down and the app reduces the damage: the crash journal `plugins-in-use.json` (offers DISABLE at the next start; sandboxed instances are not journaled), recovery snapshots of the project every 60 s and after state captures (last three, never over the user's file), and a panic boundary around `process`.
- **The sandbox** ([plugin-sandbox](../crates/plugin-sandbox/src), [plugin-ipc](../crates/plugin-ipc/src), [plugin-hostd](../crates/plugin-hostd/src)). `SandboxBackend` is a `PluginBackend` like the format backends: `instantiate` starts one `atomik-plugin-host <format> <file> <id> --block <path> --doorbell <name> --parent-pid <pid>` child per instance (next to the app, or `atomik --plugin-host`; `atomik-render` finds it next to itself). The child hosts the instance with the real CLAP or VST3 backend; its main thread is the plugin main thread (control channel, timers, the editor window) and an audio thread serves the shared block. The parent never loads a plugin file.
  - *Control channel.* The child's stdin and stdout carry frames (a little-endian `u32` length, a JSON message, an optional binary payload such as a state blob). Every request has an id and exactly one reply; plugin callbacks come back as notifications and reach the instance's `HostMessenger` on a reader thread. The child sends every pending notification before each reply, and a bounce asks for a `Flush` after every batch, so a callback reaches the host before the next batch exactly as in process (a bounce counts in batches, never in time). Main-thread calls have timeouts (10 s create, activate and state; 2 s otherwise; 250 ms param text); a timeout kills the child. The child takes a private handle to its real stdout for frames and points its stdout at stderr (`take_frame_stdout`), so a plugin that prints cannot corrupt the stream.
  - *Audio.* One shared block per instance (a mapped file of 50 944 bytes: header, one request area, one response area, raw `f32` bits and fixed-capacity events), exchanged by sequence numbers. `RemoteProcessor::process` copies the block in, rings the doorbell (Windows named event, Linux shared futex, macOS shared ulock; one atomic swap and no system call while the child is awake) and spins until the answer, the death flag or the deadline. Live, the deadline is one batch period: a late answer gives `ProcessStatus::Late` (dry for an effect, silence otherwise, the `late` meter counts it), and the events of a batch that could not be sent are carried to the next one at offset 0, so a note-off is never lost. A bounce (`SandboxConfig::bounce`, set by `atomik-render`, also for `--plugin-mode realtime`) and an offline instance wait for every batch up to a 30 s watchdog, so a sandboxed bounce is byte-identical to an in-process one.
  - *Crash.* When the child ends, the reader thread marks the block dead (`DeathHandle`) and posts `ProcessExited` with the exit code or signal and the last stderr lines; the next `process` returns `Lost`, the device turns `Crashed` (dry or silent, never called again), and the manager emits `ManagerEvent::Crashed`. A lost instance fails every call at once; `restart` and `reload` refuse it, and the app's RELOAD creates a new instance from the document's last captured state and the rack's params.
  - *Editors.* A sandboxed instance has an `EditorKind::External` editor: the child opens a top-level window, owned by the app's main window on Windows, and reports `GuiClosed`. The app creates no window for it.
  - *Tests.* The wire ([plugin-ipc/tests](../crates/plugin-ipc/tests): layout, exchange, cross-process doorbell, no-alloc, stdout protection), the parent with a fake child ([plugin-sandbox/src/tests](../crates/plugin-sandbox/src/tests)), the child driven directly and end to end through `SandboxBackend`, the manager and the engine ([plugin-hostd/tests](../crates/plugin-hostd/tests): bit-identical to in process for the CLAP and VST3 test plugins across blocks and workers, crash, kill and reload, hangs, latency restarts, state, a plugin that prints), and [render/tests/plugin_sandbox_bounce.rs](../crates/render/tests/plugin_sandbox_bounce.rs) (both plugin demos bounced byte-identical with the sandbox on and off, offline and realtime). The child's built-in `null` test plugins are selected with `ATOMIK_PLUGIN_HOST_FORMAT=null`, a test hook.
- **The VST3 backend** ([plugin-vst3/src](../crates/plugin-vst3/src)). `module.rs` loads a `.vst3` file or bundle per OS (Windows DLL and `InitDll`, macOS bundle and `bundleEntry`, Linux `ModuleEntry`) and keeps the module alive while a plugin of it lives; `layout.rs` lists the audio classes, negotiates the buses (stereo or mono main, an optional stereo sidechain, everything else deactivated, surround refused with the reason) and reads params (hidden, read-only and program-change ones skipped, units as modules), `IMidiMapping` and note-expression support; `instance.rs` is the main-thread half (component and controller created and connected through two proxies so neither holds the other, the controller brought in step with the component's state, the host `IComponentHandler`, the editor `IPlugView` with an `IPlugFrame` that is also an `IRunLoop`); `processor.rs` is the audio half (fixed-capacity `IParameterChanges` and `IEventList`, `silenceFlags` per channel, `ProcessContext` from the batch transport, host note ids, pitch bend and CCs through `IMidiMapping`, per-note expressions, output notes back as `notes_out`). Params are the **normalised** value, a stepped one (`stepCount` > 0) its step index. In VST3 the controller talks to the processor only through the host, so an editor's `performEdit` is pushed to the processor at the next batch and every value the rack sets is mirrored to `setParamNormalized` on the main thread, so an open editor and the saved controller state follow the rack. The state blob is `AVS1` + the component section + the controller section (each a little-endian `u32` length and its bytes); restore is `setState`, `setComponentState`, then the controller's own `setState`. The editor is hosted in the same separate window as a CLAP one; on Linux only the `IRunLoop` timers are pumped (file-descriptor handlers are not: such an editor stays dead and PARAMS is the fallback).
- **Render.** `atomik-render` builds plugin devices through the same manager (`render/src/plugins.rs`; both backends, a file routed to its backend by its format, `format_of_file`) after registering the installed plugins before the project loads. `--allow-plugins` is required (exit 2 otherwise), `--plugin-mode offline|realtime` (offline by default; realtime matches what was heard), `--missing-plugins error|stand-in`, `--plugin-cache`. The report line says `plugins: N (determinism not guaranteed)`. A project with real plugins is bounced by `render/src/plugin_pass.rs` instead of the plain offline loop: a silent **pre-roll** (transport stopped) until no plugin has restarted or changed its latency for 8 batches, then the song in **64-frame batches**, with a plugin-manager poll and, when the engine published a new device latency, a routing recompile (`Graph::topology`, `EngineHandle::fill_latencies`, `submit_routing`) after **every batch**: the offline form of `AppCore::frame`. Counted in batches, never in time, so it is deterministic and independent of workers (and `--block` has no effect on a plugin project); a bounce therefore has the delay compensation a project has live, from its first frame, and follows a latency that changes mid-song.
- **Determinism, defined.** The host feeds the plugin identical inputs (64-frame blocks, event offsets and order, param values, transport, note ids) for any host block and worker count, so the output is bit-identical for plugins that are deterministic functions of their inputs (all the test plugins). Real plugins that use time, random seeds or hardware state are not, bounce is not guaranteed equal to live for them, and golden hashes are never taken over real plugins.
- **Tests as proof.** `plugin-host/tests/engine_integration.rs`, `plugin-clap/tests/engine_clap.rs` and `plugin-vst3/tests/{process,lifecycle,state,engine,leak,cross_format,vst3_host}.rs` (the suites loop over both formats; the CLAP and the VST3 test effect give the same bits) (the chain equals the reference DSP and is bit-identical across blocks and workers under the allocation guard, PDC from a reported and a changed latency, thread-check per worker count, a restart in the middle of a render), `plugin-clap/tests/{process,lifecycle,state,gui,leak,crash,hang}.rs` against the real backend and the test plugins, `plugin-scan/tests/scanner.rs` (real child process), `render/tests/plugin_demo.rs`, `plugin_demo_vst3.rs` and the app's `app_core_plugins*_tests.rs` (live equals the realtime bounce, including a saved latency and a latency that moves mid-song in both formats, stand-ins, one instance per frame, engine restart keeps instances, journal and snapshots, `LayoutChanged` and relink rebuilds), `--stress-plugins` and the 200-add-and-remove and 500-instance loops. Examples: `examples/projects/plugin-demo` (CLAP) and `plugin-demo-vst3` (both formats in one project).
- **Known limits.** Linux VST3 editors that need file-descriptor handlers are dead (timers work); no about box (the VST trademark line is in `--help`, the README and DEVICES.md); editor window positions are not remembered across sessions; no Wayland embedding for either format; macOS and Linux paths are compile-checked (type-checked and linted) but have not been run against real plugins; the sandbox's Linux and macOS wake-up and stdout redirection are compile-checked only; one process per instance costs memory with many instances; a sandboxed editor is a separate window, not embedded.

## 6g. Input, commands and the keymap

Every key the app understands goes through one registry, one data-driven keymap and one router. The cheat sheet is [KEYBOARD.md](KEYBOARD.md). The standard default profile, the daily keys and the tool palette are described in the **Daily keys** bullets below, the clipboard, rack multi-selection and the context menus in the **Clipboard, selection and context menus** bullet, and the auto-routing creation chain in the **Creation chain** bullet.

- **Registry and keymap data** ([ui/src/keymap](../crates/ui/src/keymap), pure, no window system). `Registry::bundled()` lists every command (134) by a stable dotted id with label, group, default context, an optional choice argument, and the flags `repeatable`, `menu` and `can_decline`. `default_keymap.json` (embedded) holds two profiles, `standard` and `legacy` (the keys of earlier versions), as `{ command, arg?, context, chords, os? }`. `Cmd` in a chord is the logical primary modifier (Control on Windows and Linux, Command on macOS); `os` overrides carry only the exceptions. `Chord::parse` and its canonical printer round-trip; `PhysChord` is a chord resolved for one OS and matched **strictly** (Control is never Command, Super never matches `Cmd` on Windows and Linux).
- **Contexts and the router.** `Context` is `Global`, `Rack`, `Sequencer`, `Editor`, `Mixer`, `Browser` or `Text`. The shell (`Shell::context_stack`) builds a `ContextStack` from the focused pane and from whether a view owns a text field (`is_text_owner()` on the rack, the sequencer and container editors, the parameter pane, the file browser and the console; the tempo field takes every key before the router). `Keymap::resolve` returns the bindings of the stack, most specific context first, then `Global`; the first command the shell can run wins, a command that cannot (a view key not migrated yet, or one that `can_decline`) falls through to the next and finally to the focused view. While `Text` is on the stack only chords with the primary modifier, function keys and Esc resolve; everything else goes to the text owner. The `Router` also tracks held keys: a press of a key already held is a repeat and reaches only `repeatable` commands (undo, redo, zoom, arrows of the editors); a lost window focus clears the held keys.
- **Input layer** (`UiEvent`, [app/src/translate.rs](../crates/app/src/translate.rs)). `Key::Numpad(NumpadKey)` and `Key::Insert` come from winit's physical key and location, so the numpad is distinct from the main row with NumLock on or off; a numpad key no command takes reaches the views as the character it types. `Key::Digit(n)` is the physical main-row digit, produced only on macOS with Command and Option held (the Mac secondaries). `UiEvent::ModifiersChanged` is emitted once per real change; releases are delivered for every key. Ctrl+click on macOS becomes a secondary click (and its release follows). Pointer gestures keep the lenient `Modifiers::command()`.
- **Menus and shortcut text** ([app/src/commands.rs](../crates/app/src/commands.rs)). `AppCommand::command_id()` and `from_command` are a bijection onto the registry's menu commands; `menus(state, keymap)` takes each item's shortcut text from the active keymap and OS (the first chord of the command), so a remap changes the menu. No shortcut string literal remains in the file (a test greps for it); native macOS accelerators derive from the same text.
- **The user keymap** ([ui/src/keymap/user.rs](../crates/ui/src/keymap/user.rs), [editor.rs](../crates/ui/src/keymap/editor.rs), [app/src/keymap_store.rs](../crates/app/src/keymap_store.rs)). `keymap.json` next to `settings.json` is a diff over the profile: an entry holds the full chord list of one (command, argument, context) in logical `Cmd` grammar for every OS and replaces the profile binding, including its OS overrides; `removed` takes a chord away; `roles` overrides the modifier roles; the chosen profile is stored too. Loading is lenient (unknown fields ignored, unknown command ids kept and not applied, wrong-shaped entries skipped with a note); a file that is not a JSON object is renamed `keymap.json.bad` and the defaults run with a status message. Saving is canonical (sorted, no timestamps) and atomic (temp file, rename). Building a keymap never fails: bad, reserved and unknown entries are dropped and listed in a `Report`; two commands on one chord in one context are a **conflict** (an error in the report), a context binding over a `Global` one is a **shadow** (a note). Reserved chords (Esc, Alt+F4, Alt+Tab and Super chords on Windows and Linux, Cmd+Q, Cmd+H, Cmd+M and Cmd+Tab on macOS, plain Space, Enter and Tab in `Text`) cannot be assigned, but a default may keep its own. The shell hot-reloads: applying the dialog swaps the router and the role table at once, and `poll_status` compares the file's modification time and size and reloads an edited or deleted file.
- **Settings tabs** ([app/src/settings_dialog.rs](../crates/app/src/settings_dialog.rs), `keyboard_tab.rs`, `workflow_tab.rs`). Audio (unchanged), Keyboard (a `KeymapEditor`: list by area, search, learn by pressing, add, clear, reset one or all, the conflict box with Swap, Unassign and Cancel, shadow notes, profile chips, modifier roles, export and import through file pickers) and Workflow (auto-route, create keeps the browser open, follow the song; saved in `workflow.json`, unknown fields kept). Nothing is saved until Apply; Cancel and Esc discard every draft.
- **Cheat sheet.** `atomik --print-keymap [--os win|mac|linux] [--profile standard|legacy] [--keymap FILE]` writes markdown from the registry and the keymap; [KEYBOARD.md](KEYBOARD.md) is its output and a test keeps them equal (`ATOMIK_UPDATE_GOLDEN=1 cargo test -p atomik-app --lib cli::` regenerates it).
- **Daily keys: dispatch** ([app/src/shell.rs](../crates/app/src/shell.rs), `Shell::run_command`). The app default profile is `standard` (`APP_DEFAULT_PROFILE`); `legacy` stays selectable. Every command of a resolved key is offered to the focused view first (`ArrangementView::command`, `PianoRollView::command`, `RackView::command`, and the step, sample and slice editors -> `CommandOutcome::{Handled, Declined, NotApplicable}`, reached through `AppCore::pane_command`), then to the shell (`run_shell_command`: the transport steps, the pane toggles, the create keys, and every `AppCommand` through `from_command`). The first that takes it wins, so a user binding in a context shadows a `Global` binding of the same chord at run time and an unbound chord does nothing in a view that used to handle it itself. The views keep `key()` only for Escape (and Home in the arrangement) and text entry (the container and sequencer editors also ignore chords with the primary modifier there, so a command chord that no binding took is never typed into a name); the sample and slice editors answer `edit.delete` (the selected zone, or the selected slice merged into the previous one; declined with nothing to remove or mid-gesture, so the next binding runs), the step editor `editor.toggle_note_mute`, and the sequencer and container editors have no command of their own (every one is declined, so the global bindings run); the console answers the `mixer.*` view commands (`ConsoleView::command`: `mixer.value_up/down` and the page and `_fine` variants step the focused control, `mixer.scroll_left/right/home/end` move the strips; Up, Down, Page Up and Down, the arrows, Home and End with and without Shift in the `Mixer` context, repeatable, rebindable, conflict-checked, in the cheat sheet), so its `key()` keeps only Escape and the F5 shortcuts and a chord no binding took does nothing; **the console text owner**: one owner for every console name edit: `ConsoleView::is_text_owner()` is true while a strip or bus name is being typed (a double-click on a name plate, or `begin_rename(strip)`; a channel renames the device whose name it shows, the source instrument's else the channel's, as one `Rename`, a bus its own name as `RenameBus`), with one buffer; the shell then reports `Text` over `Mixer`, so only primary-modifier chords, function keys and Esc run commands, Space and Delete are text, Enter commits (an empty or unchanged name commits nothing), Esc cancels, a pointer press elsewhere commits like Enter, losing the focus cancels, and a command chord is never typed in; undo, redo, the transport keys, select all, duplicate, delete, split, quantize, transpose, nudge, zoom, snap, follow and the tools are commands.
- **Daily keys: tools, roles, zoom, follow** ([ui/src/viewport.rs](../crates/ui/src/viewport.rs), `ViewportState`, one per time view). `Tool` is Select, Pencil, Eraser or Razor (`tool.*` commands, toolbar buttons in the arrangement corner and the piano roll top bar, the active tool lit). Select keeps today's modeless gestures; the pencil makes a plain click draw (a one-bar clip, a note) and ignores clips and notes; the eraser deletes the clip, note or automation point under the pointer; the razor splits a clip or note at the snapped pointer position and a razor click in the arrangement ruler splits every clip crossing it. The **alternate-tool role** (a hold) switches the tool for one gesture (Select -> Pencil, any other tool -> Select) and shows on the toolbar from `ModifiersChanged` alone (`Shell::forward_modifiers`); **disable snap** is the Ctrl+Alt hold (`Roles`; the legacy roles keep Alt alone for it and have no alternate tool, `Roles::legacy`). `sequencer.snap_toggle` (S) switches snap off and back to the previous value; `view.zoom_in/out` (H, G, Ctrl+=, Ctrl+-) are time zoom in the sequencer and the editor and rack zoom in the rack (the views claim them when focused, the rack declines and the shell zooms it); `sequencer.zoom_selection` (Z) fits the selected clips or notes and, again, the whole song or clip (`TimeAxis::fit_span`); `sequencer.follow` (F) pages the view to the playhead while the transport runs (`TimeAxis::page_to`), a manual scroll pauses it until the next toggle or stop, and the Workflow preference `follow_song` is its start state. **Nudge** in the piano roll: `editor.nudge_left/right` move the selected notes by the snap step, `editor.nudge_left_beat/right_beat` by one beat of the meter (`Meter::beat_ticks`, the Beat snap step) and `editor.nudge_left_tick/right_tick` by one tick, whatever the snap (Shift+arrow and Alt+arrow in the legacy profile, `Cmd+Shift+arrow` and `Cmd+Alt+arrow` in the standard one). All are repeatable, clamp the group at tick 0 and are one undo step per press (`move_selection`). The arrangement has no move-by-step path for clips, so it has no nudge.
- **Daily keys: transport, panes, create.** `AppCore` gained `locate_bars`, `go_locator`, `stop_or_rewind` (a second Stop returns to the start), `nudge_tempo` ([app/src/app_core_workflow.rs](../crates/app/src/app_core_workflow.rs)); the numpad transport keys, `C`/`L`/`Ctrl+Enter` and the locators are registry commands. F6 (`rack_visible`, saved in `workflow.json`, not in the project) hides the rack and moves the transport bar to the top; F7 hides the rack and the console and remembers the layout it replaced; F8 and Shift+Tab close the open editor or open the editor of the selected clip; Enter in the arrangement opens the selected note clip and falls back to return to zero; K cycles the cable display; the macOS secondaries `Cmd+Opt+<digit>` are the same commands by physical digit. `create.instrument` and `create.effect` open the device browser in **create mode** (`RackView::open_browser_create(CreateKind)`: the list is filtered to instruments or effects, the filter is focused, Enter adds the highlighted device through the existing `AddDevice` and closes the browser unless the Workflow setting says otherwise, Esc cancels); `create.audio_track` is `AddAudioTrack` and `create.mixer_channel` opens the console's add-channel picker. The same Enter (and the double-click add) creates through the creation chain described below.
- **The one-time notice.** On the first start with the `standard` profile and a settings folder, the status bar lists the keys that moved, printed for the OS from the active keymap (`Shell::keys_notice`); `keys_notice_seen` in `workflow.json` keeps it from showing again.
- **Clipboard, selection and context menus.** *Rack selection* ([ui/src/rack/selection.rs](../crates/ui/src/rack/selection.rs)): `RackView` keeps a set of selected devices with a primary (the last clicked: `selected()`, what the editors and the live keyboard follow) and an anchor; the toggle and range **roles** (`Role::ToggleSelect`, `Role::RangeSelect`, handed to the rack by `AppCore::set_roles` like to the time views) decide Ctrl or Cmd click and Shift click, so the OS is a role-table parameter; a click on empty rack clears (so does Escape when no drag, menu or focused control is pending), a plain press on a member of a group keeps it for a group drag and collapses on release, a right click on a member keeps the group. `UiAction::Select` reports one device, `UiAction::SelectMany { primary, keys }` several (path keys inside a container). The selection commands are registry commands the rack answers (`edit.select_all`, `edit.delete` -> `RemoveDevices`, `edit.duplicate` -> `DuplicateDevices`, `rack.select_next/prev`, `rack.extend_next/prev`, `rack.disconnect` -> `DisconnectDevice`); a group drag ends in one `MoveDevicesToSlot` (`MoveDevices` inside a container; never a no-op). The arrangement gained a track selection (header click, Up and Down) and an automation-point selection; Join, Duplicate (`DuplicateClips`, `DuplicateTrack`, `DuplicatePoints`) and Delete (`RemoveClips`, `RemoveTrack`, the points) are workflow commands, so each is one undo step; the piano roll duplicates notes (`DuplicateNotes`). *Clipboard* ([app/src/clipboard.rs](../crates/app/src/clipboard.rs), [app_core_clipboard.rs](../crates/app/src/app_core_clipboard.rs)): `Clipboard` holds one typed `ClipboardData` (`Clips`, `Notes`, `AutomationPoints`, `Devices`, `Tracks`, the snapshots of `atomik_model::workflow`) in `AppCore`, which New and Open keep, so a copy survives both; there is no OS clipboard. Copy, cut and paste of the focused pane run in `AppCore::clipboard_command` (cut is copy then the view's own delete): clips and points paste at the playhead (on the selected track when there is one), notes at the playhead inside the open clip, devices after the primary device (inside the open container), tracks after the selected track; a repeated paste advances the playhead by the span of what was pasted unless the transport runs. `AppCore::apply_command` wraps every `WorkflowCommand`: before it, a paste registers the pool entries its snapshot needs (`RegisterAsset`, not an undo step); after it, the pasted clips (from `next_clip_id`), devices, notes and points are selected. A refusal (empty or foreign clipboard, nothing selected) is a status message. *Context menus* ([ui/src/context_menu.rs](../crates/ui/src/context_menu.rs), [app/src/context_menus.rs](../crates/app/src/context_menus.rs)): a right click makes the view emit `UiAction::ContextMenu { target, at }`; the shell builds a `ContextMenu` from a list of registry command ids (labels from the registry, shortcut text from the active keymap and OS, enabling from the selection and the clipboard), shows it as a modal overlay (Escape, a click elsewhere or a resize closes it, keys are swallowed) and runs the chosen command through `Shell::run_command` in the pane the menu belongs to, the path a key press takes. Menus: device, empty rack, track header, clip, empty lane, piano-roll grid; a right click on a note still deletes it. The Edit menu has Cut, Copy, Paste, Duplicate, Delete and Select All with live enabling.
- **Creation chain.** Creating a device that wires itself is a model command, one undo step, planned on a scratch copy ([model/src/workflow_create.rs](../crates/model/src/workflow_create.rs)): `WorkflowCommand::CreateInstrument { index, source, key, options }` adds the device (its console channel and the master come from the `AddDevice` rule), its song track when it has a Notes input, the track armed, and disarms the tracks named in `options.disarm`; `CreateEffect { source, target, key, options }` routes by rule (the selected channel, or the channel made for the selected instrument, gets the effect in its first free insert slot; the selected FX return effect gets it in series on the return; another top-level device with free audio outputs gets it right after it, cabled stereo; anything else, a full chain, a non-stereo effect or the master only adds it); `AutoRoute { devices, options }` applies the same rules to existing devices (an instrument without channel or track, a loose effect); `DisconnectDevices` cuts every cable of several devices; `DeleteDevices` removes like `RemoveDevices` and bridges the audio path of a removed effect where it is unambiguous. `CreateOptions { route, skip_track, disarm }`: `route == false` is exactly the plain add. The model cannot know which tracks an earlier auto-route armed (the format has no flag), so `AppCore` keeps that list for the session (`auto_armed`, cleared by New and Open, [app/src/app_core_create.rs](../crates/app/src/app_core_create.rs)) and passes it as `disarm`; after the command it selects the new device so `notes_target` plays it, and names what was made in a status message. The rack view builds the commands: the browser Enter and the double-click add use them for instruments and effects (built-in and plugins) at the top level (dragging a browser row uses the slot variants `CreateInstrumentAt` and `CreateEffectAt`, and the app fills `disarm` for both), with `route` = the Workflow setting `auto_route` inverted by Shift and `skip_track` = Alt; inside a container the plain add stays. Delete bridges only with auto-routing on. `rack.auto_route` and `rack.disconnect` work on the whole selection. *Branch order of `CreateEffect`* (one scratch copy per rule, a rule that cannot be done falls back to the plain add, so creating never fails): route off, or an effect that is not a stereo effect: added only; the master: added only; a channel or the instrument it was made for: the first free insert slot (four slots), the effect right after the chain; the effect of an FX return: in series on that return; any other top-level device with free stereo outputs: right after it, cabled; otherwise added after the selection or at the end. *Bridging* (`DeleteDevices`): only a top-level effect, utility or container with audio sockets; each audio input socket with exactly one cable joins the output of its own side (a single connected input and output pair whatever the names) and its source is cabled to every destination of that output; nothing is bridged for an ambiguous input, console devices, instruments, mixers, the insert loop of a channel, an FX return effect or anything inside a container, and a bridge the cable rules refuse leaves the removal plain. `RemoveDevices` and `AddDevice` are unchanged. Proof: `model/tests/workflow_create{,_props}.rs`, `ui/tests/workflow_create.rs`, `app` `app_core_create_tests` (including live equals bounce for a created project) and `shell_create_tests` (run for three operating systems).
- **What is not here yet.** Bridging inside containers; and a gesture that starts a console STRIP name edit from the keyboard (a double-click on a name plate edits it, `begin_rename` is the programmatic start).
- **Tests as proof.** `keymap::{chord,command,context,conflict,roles,script,sheet,tests,user_tests}`, `ui/tests/keymap_goldens.rs` (the six listings `ui/tests/keymaps/{win,mac,linux}-{standard,legacy}.txt`), `app` `shell::{keys_tests,keymap_tests,qa_tests,workflow_tests}`, `ui/tests/{workflow_arrangement,workflow_piano_roll,workflow_rack,workflow_snapshot}.rs`, `settings_tabs_tests`, `keymap_store`, `commands::tests`, `translate::tests`, `cli::tests`, `model/tests/workflow_{devices,clipboard,props,create,create_props}.rs`, `ui/tests/{workflow_selection,workflow_arrangement_selection,workflow_create}.rs`, and `app` `app_core_clipboard_tests`, `shell_clipboard_tests`, `clipboard`, `context_menus`, `app_core_create_tests` (with the live-equals-bounce test of a created project) and `shell_create_tests`. ## 6h. The master section and Audio I/O

The master section and the Audio I/O device are first-class citizens of the rack. No project-format change (version 9), no change to the routing plan, summing order, PDC or stages.

- **Starter document.** `atomik_model::new_project_doc()` is `empty_doc()` plus the master (key `master`, name "Master", first in `devices`, unfolded) and the cables `master:main_l/r -> interface:out_1/2`; it is built with the same helpers as the master creation of `AddDevice`, is deterministic and saves byte-identically (golden `model/tests/golden/new_project.json`). The app uses it for File, New, for a start without a file (`Cli::start_document`; the stress options keep their generated racks) and nowhere else: Open, patch load and the render CLI never create a master, so old and foreign files load unchanged. `AppCore::new` and `with_doc` keep taking the document they are given (tests build rack-only documents with `empty_doc()`).
- **Master is fixed.** Command level only (never a load error): delete, cut, copy and moves of the master, and anything placed above it while it is the first device, are rejected with `ModelError::Fixed` (or clamped to index 1 for adds and pastes). The UI shows the message ("The Master Section cannot be deleted") like any rejection.
- **Console links are a display.** `console::link_kind` classifies a cable as a console link (channel or bus `out` to the master or a bus, `send{k}` to master `send_bus{k}`) and `console::output_dest` reads where a channel or bus goes; the rack hides the links unless "Show Console Links" is on and paints "Output: Master", "Output: Bus <name>" or "Output: Audio I/O 3+4" on the plate. The cables, and so the compile, are the same.
- **Auto-assign.** `CreateEffect` with the master selected puts the effect on the lowest free send/return (`SetReturn`, one undo step); all eight used adds it unrouted. `AssignSend` ("Use as Send Effect", `rack.assign_send`) does the same for an existing effect. The model decides (`effect_route_note`, `first_free_send_slot`); the app only passes the selection and shows the text: `AppCore::created` reports "Effect routed to send/return N" or "All 8 send and return slots are in use" ([app/src/app_core_create.rs](../crates/app/src/app_core_create.rs)).
- **Master additions.** `send1.level` to `send8.level` (appended ids, 0 dB bit-exact), an 18-entry `monitor.source` (taps kept in device state), and the key switch that turns on with a cable into `key_in` (one undo step). See [DEVICES.md](DEVICES.md).
- **One name.** "Audio I/O" everywhere a user reads it (type id and key `interface` unchanged); a grep test (`ui/tests/single_name.rs`) guards it.
- **Audio I/O data in the app** ([app/src/app_core_io.rs](../crates/app/src/app_core_io.rs)). `EngineSink::host_channels()` gives the channel counts of the running stream (`LiveSession` keeps them from `StreamInfo`; the offline sink and a stopped session say `None`, all channels available); `AppCore::frame` and every engine start pass them to `RackView::set_io_host_channels`, which derives the lamp colours (green connected, yellow free, red cabled but missing on the device). `AppCore::feed_io_meters` runs once per frame and gives `RackView::set_io_peaks` the peak per socket: **inputs** are metered at the interface's own `in_k` output endpoints, **outputs** `out_k` (audio inputs of the interface, which the engine cannot meter by endpoint) take the largest peak of the *source* endpoints of the cables that end there. The meters are the engine's existing read-only bank (`Topology::add_meter`, planned when the routing is submitted, reused buffers, no allocation per frame) and touch no sample (test: live equals bounce with the feed running every block). A meter read resets its peak, so an endpoint the console strips also meter (the master's `main`) is read once per frame and the reading is shared with `update_console_meters` of the same frame.
- **First start.** `ui-state.json` gains `console_notice_seen`; the first start with a state file says once that console devices are shown now and where the toggle is (not for a user who switched them off).
- **Example.** `examples/projects/master-demo` (starter, Lead and Bass, a reverb on send and return 1, a master send level), generated by `render/tests/master_demo.rs`.
- **Tests.** `render/tests/old_projects_4m.rs` pins that every committed example project is still format 9 and saves back byte for byte, and that Open creates a master only in a file that had one.

## 6i. Factory devices: `atomik.character`

Original built-in devices are built with one repeatable pipeline; `atomik.character` is the most elaborate. See its section in [DEVICES.md](DEVICES.md).

- **DSP stage blocks** (`atomik-dsp`): `shaper` (curves, level-dependent dynamic type, optional first-order antiderivative anti-aliasing), `leveller`, `crossover` (fourth-order, flat sum), `phaser`, `chorus`, `echo` (glide rule), `comb`, `room` (a parametrisation of `fdn`), `ringmod`, `bitcrush`, `noise` (white, pink, rumble, `Crackle`, `Wander` and the programme-presence gate), `spectral` (an STFT frame processor with the algorithms identity, gate with hold, slew, band-pass, band-stop, quantise and the combined `Lossy`), `modal`, `wobble` and `smoother2`. All are allocation-free after `new`, chunk-invariant, flush denormals and keep libm out of the per-sample path (`det_math`, `det_trig`); `crates/dsp/tests/stage_blocks.rs` pins a render hash per block configuration so a platform difference shows on the macOS run.
- **Device** (`atomik-devices`, `character.rs` and `character/`): the engine batch of 64 frames runs as four 16-frame control blocks; per block the CV smoothers (8 ms, second order), the Transform morph (`voicing::PresetVoicing::resolve`) and the active chain run. Gain and volume are `4 x^2` on a linear knob; the dry tap sits **before** the input gain and is delayed by the active preset's latency, so Dry/Wet 0 is the input delayed, bit for bit. Sixteen chains are built in `prepare`; a preset change is a 30 ms smoothstep crossfade of the outgoing and incoming chain (the incoming one starts reset, the outgoing one is reset when the fade ends, a request during a fade is queued and the last wins).
- **Rack and voicing as data.** `rack.rs` is a generic stage graph (`RackChain`): per-stage sends, a load-time acyclic and reachability check, lazy evaluation (a stage no active route reaches does not run and keeps its state), automatic delay alignment of parallel paths. The numbers live in `data/character-voicing.csv` and `data/character-routes.csv` (embedded with `include_str!`). Only `wide` is hand-wired (`row2.rs`).
- **Tiered latency.** Every preset except `lossy` is in the short class (`29 + wobble centre`: 45, 46, 60 frames at 44.1, 48, 96 kHz); `lossy`, the only preset on the spectral stage, is in the long class (`+ the frame`: 1069, 1070, 2108 frames). A preset change inside a class never moves the latency; one across the classes publishes it once, when the fade ends (one engine `latency_epoch` bump).
- **The bounce follows the latency epoch.** The live app recompiles the routing when the epoch moves; the plain bounce does the same (`atomik_render::plugin_pass::render_song_following_latency`: 64-frame batches, routing recompiled after the batch), so a live run and a bounce of a project that crosses the classes agree. The plain bounce therefore no longer renders in `--block` sized chunks (output is identical for every block by construction).
- **UI and app.** `FxKind::Character` with four meter values; `character_panel.rs` (the 4 x 4 matrix as one focusable widget, knobs, screen, back panel with the CV trims), `character_screen.rs` (16 procedural glyphs and scenes); the app feeds the meters through the generic `meter_count() > 0` rule (inside containers by path key) and adds `--stress-character` (8 containers cycling through all 16 presets under macro lanes). `atomik-ui` repeats the one-line gain law and the preset tables and pins them to the device in tests (the UI links no device code).

## 6j. The file browser

A docked panel on the left of the window (View, File Browser, `F4`) lists folders and audio files, plays the selected file at once, and drags files onto the other panes. It adds the crate `atomik-library`, the preview voice in the engine, and three workers and a saver in the app. It changes no project format and no routing, and it never writes, moves or deletes a user's audio file: the only file it writes is the library file (with its `.tmp` and `.bad` companions).

- **The panel** ([ui/src/file_browser.rs](../crates/ui/src/file_browser.rs) and `file_browser/`). A folder tree over a file list. The tree has Favourites, Tags (one child per tag with its count), Bookmarks, then the drives and the home folder; folders expand lazily. The list shows folders first, then audio files (wav, aif/aiff, flac, mp3, ogg), in a natural order ("kick 2" before "kick 10"); the columns that fit are star, name, duration and, when wide, channels, rate and size. The search field filters as you type with the language of `atomik_library::Query`: words match the name (case-insensitive, all words), `#tag` matches a tag, `fav` keeps favourites; a toggle searches the sub-folders too. The view owns the query, sort, selection, scroll, expansion and the filtered index list, and paints only the visible rows, so painting does not grow with the folder size. It does no disk access: the app pushes everything it shows (`set_places`, `set_children`, `set_location`, `set_rows`, `append_rows`, `patch_info`, `patch_marks`, `set_preview`) and answers the `UiAction::Browse(BrowseAction)` actions it emits (navigate, show a `Place`, preview, favourite, tags, bookmarks, `RequestInfo`, `DragFiles`). In the list, `Ctrl+A` (`Cmd+A`) selects all rows.
- **The core and its workers** ([app/src/app_core_browser.rs](../crates/app/src/app_core_browser.rs), [browser_workers.rs](../crates/app/src/browser_workers.rs)). The UI thread never touches the disk for the browser: it sends jobs and `AppCore::frame` drains the answers. `atomik-browse` lists a folder (`read_dir` and metadata), the sub-folders of a tree node, the drives, the files of a favourite or tag place, and walks the sub-folders for the recursive search (results stream in batches, capped at 100 000 entries). `atomik-probe` reads audio headers for the rows the view asks for, visible rows first, and the results patch the rows by path. Every listing, walk and lookup carries a generation, so a newer request makes older answers stale and stops a running walk. Folders are not watched: a folder is listed again when it is shown and on refresh.
- **The library file** ([app/src/library_store.rs](../crates/app/src/library_store.rs), [library/src/db.rs](../crates/library/src/db.rs)). `<config_dir>/library.json` holds favourites, tags and bookmarked folders, keyed by `PathKey` (a lexical normal form of the path: `/` separators, case-folded on Windows): `{"version":1,"places":["/home/me/samples"],"entries":{"/home/me/samples/kick.wav":{"favorite":true,"tags":["808"]}}}`. Entries with no tag and no favourite flag are removed, and the output is deterministic (ordered maps). The file is read once when the path is set. A file that is not valid is renamed `library.json.bad` (replacing an older one), and the app starts with an empty library and says so in the status bar. A file with a newer version, or one that cannot be read, is never overwritten: the library stays in memory only. A change marks the database dirty; the next frame hands a JSON snapshot to `atomik-library-save`, which writes a temporary file and renames it (one write in flight, the newest snapshot wins). `Shell::shutdown` flushes the library synchronously.
- **The preview path** ([engine/src/preview.rs](../crates/engine/src/preview.rs), [audio-file/src/stream_decode.rs](../crates/audio-file/src/stream_decode.rs)). On a click the UI thread creates the channel with `preview_channel()` and starts the voice at once with `EngineHandle::preview_start(stream, gain)` (`ControlOp::PreviewStart`); the feed goes to `atomik-preview`, which opens the file with `StreamDecoder`, calls `PreviewFeed::set_source_rate`, and pushes decoded chunks (a small first chunk, then larger ones) until the end of the file, an abandoned stream or a newer preview. The voice is *pending* until the decoder has set the rate and pushed data: it is silent, counts no underrun and its fade does not advance, and the previous stream fades out meanwhile. The decoder never runs more than the ring (65 536 frames) ahead, so a long file is never decoded whole. The voice resamples from the file's rate with cubic Hermite interpolation (bit-exact passthrough at equal rates), fades in over 5 ms, fades the old stream out over 5 ms on a switch or a stop (the crossfade sums to unity), and is mixed into interface outputs 1 and 2 after the metronome, outside the routing and the master meters. An empty ring before the end of the stream is silence, counted, never a wait. Finished or replaced streams go back through the retire queue (`Retired::Preview`), so the audio thread never frees. The panel shows progress from a `PreviewMonitor` (frames played, done, underruns). A preview is live only (see HI-2).
- **Drag to other panes.** `BrowseAction::DragFiles` hands the gesture to the shell (`Capture::FileDrag`). Moves become `UiEvent::FileHover` over the pane under the pointer and the release becomes `UiEvent::FileDrop`, through the same path as an OS file drop, so the arrangement, the sample editor and sampler panels react as they do to a drop from the desktop. A release over the panel, over a pane that takes no files, or after Esc cancels.
- **Keys.** The panel is the key context `Files` (over `Global`): while it has the focus, its keys are the `files.*` commands, which the shell hands to the panel as the keys they stand for; they win over global chords of the same keys (Space previews instead of playing, Backspace goes up a folder). While the search or tag field owns the keyboard the context is `Text` over `Files`. `view.toggle_file_browser` (`F4`) is global. The full list is in [KEYBOARD.md](KEYBOARD.md).
- **Persistence.** `ui-state.json` keeps the panel's visibility, width, tree/list split, the auto-preview switch and the last folder. `atomik --file-browser [DIR]` shows the panel at start, on `DIR` when given.

## 7. The UI crate

`atomik-ui` has no window-system dependency and no time source. The app feeds `UiEvent`s and applies the returned `UiAction`s; views draw through the `Canvas` trait into a display list (tested with JSON goldens), and only `scene_canvas.rs` talks to the GPU (vello). Views: the rack, the arrangement (with audio clips, waveforms, fade, gain and trim handles, the input selector and file-drop mapping), the piano roll, the console, the transport bar, the device browser, the file browser panel (6j) and the sample editor. The audio maths (tempo map, waveform columns, handle mapping, input cable sets) is pure and headless in [ui/src/audio.rs](../crates/ui/src/audio.rs). The sample editor ([ui/src/sample_editor.rs](../crates/ui/src/sample_editor.rs)) replaces the arrangement like the piano roll: a key × velocity map of the zones, a zone list, the selected zone's waveform with start, end, loop and crossfade markers and numeric fields. The drum machine has its own rack panel (`autolayout::drum_layout`): a 4×4 pad grid (click selects and auditions, drops load the pad), the eight knobs of the selected pad (view state, remapped onto `padN.*`), master level and an Edit button, and a back panel that groups the sockets per pad (outputs and gates) with the two global CV jacks and trims in a CV section.

The slicer's rack panel (`autolayout::slicer_layout`) adds an overview strip, a sensitivity knob (view state), the Slice, To track and Edit buttons and the device knobs.

## 9. The audio interface pseudo-device

`Graph::new` creates device id 0, `Graph::INTERFACE`, with type id `atomik.audio-interface`.

- Its sockets `in_1..in_N` are Audio **outputs**: host input enters the graph through them. This is where an audio track's input cables start.
- Its sockets `out_1..out_M` are Audio **inputs**: host output leaves the graph through them.
- It is a pure source and a pure sink, so `in_k → … → out_j` is never a cycle.
- At most 32 channels each way (`MAX_INTERFACE_CHANNELS`).
- Its descriptor is built once per channel combination and cached. This happens off the render path. See [crates/engine/src/interface.rs](../crates/engine/src/interface.rs); the UI and the model name the same sockets.

## 10. Known limitations

- **Params are quantised to batch boundaries.** A param message takes effect at the next 64-frame boundary; devices smooth audible params themselves. Notes are sample-accurate. Song automation is applied once per batch.
- **No time-stretch.** Audio clips keep their timing when the tempo changes.
- **No relink for missing audio files.** They are reported, and their clips play silence.
- **Sampler scope.** One interpolation mode (cubic Hermite), no round-robin, release samples, per-zone envelopes or filters, no zero-crossing snap, and zones are RAM-only. A bounce stops with an error on a missing zone asset, while the live app plays silence.
- **Drum machine and slicer scope.** No flam or ratchets, per-pad filters, kit presets, time-stretch inside slices or REX import; the slicer is one loop with at most 64 slices.
- **Effects.** The limiter's true-peak detection is the BS.1770 4x one; a 16x oversampled reference reads full-band white noise up to about 1 dB over the ceiling. Changing the compressor look-ahead or the distortion oversampling changes the reported latency and makes one audible discontinuity at the change. No linear-phase EQ, no FFT analyser.
- **Players.** The sequencer is monophonic (one note per step, no chords, ratchets or flams), has no pattern chains or song mode and plays only with the transport; the arpeggiator has no free (Hz) rate and no note filters; neither records its output to a clip.
- **Containers.** No standalone container presets, no group or ungroup, no cut and paste across scopes, no container bypass, level or CPU meter, linear macros only, one split per target instrument, no CV or sidechain sockets on the boundary, and `export_patch` writes a container without its inside (patches are flat; the project file keeps it). The container editor has no View-menu entry (EDIT on the panel opens it).
- **Recordings and streaming.** A recorded lap is read back into RAM before the app decides whether to stream it, and the reported device latency can miss buffering that a driver does not report; the user offset in the settings corrects that.
- **Feedback loops are rejected.** A cable that would close a loop returns `WouldCreateCycle`; insert and return loops use stages instead.
- **Platform-dependent last bits.** Output is bit-identical across host block sizes and worker counts on one platform. Across operating systems, math-library differences can change the last bits, which is why the SHA-256 golden is checked on Windows x86-64 only (see [TESTING.md](TESTING.md#golden-files)).
- **Plugins.** Sandboxed (the default), each instance is a process of its own and its editor a separate window; a live batch that the child answers late passes dry. In process, a native crash takes the app down (the crash journal and recovery snapshots limit the damage). The plugin is always called with 64-frame blocks, so a plugin that prefers large blocks costs more CPU. Bit-identical output is guaranteed only for plugins that are deterministic functions of their inputs (the test plugins); real plugins that use time or random seeds are not, and a bounce is not guaranteed to equal what was heard.  no Wayland embedding (the PARAMS pane is the fallback), a patch change made in the plugin's own window is not undoable, a change made there outside a gesture is not shown until the state is captured, pins default to the first eight params (not the plugin's remote-controls page), window positions are not remembered across runs, recovery snapshots hold the project file without its audio bundle, and surround, multi-output and MPE are not supported.
- **No note chase** on play or locate.
- **File browser.** Tags and favourites are keyed by path, so moving or renaming a file outside the app loses them. A preview plays at 0 dB with no level control and no cue output, and the browser shows no waveform. The tree does not expand to reveal the folder shown in the list. Folders are not watched; they are listed again when shown or refreshed. A third preview start within 5 ms of a switch cuts the oldest stream (the voice has two slots). Dropping a browser drag onto the transport bar or the console cancels it (an OS drop there imports the files at the playhead). The browser lists audio files only: devices, patches and projects are not in it.
