# Roadmap

This is a list of intentions, not promises. There are no dates. The phases are in rough priority order, but items inside a phase are not ordered. Ideas and help are welcome: open a discussion or an issue before starting something big.

Design questions that shape several items (plugin batching, ASIO licensing, delay compensation, the patch format, modulation, note naming, format cadence and more) are recorded with their options and status in the [decision log](docs/DECISIONS.md).

## Phase 1: Stability and platforms

- **Sync follow-ups.** Audio clips stretched to the followed tempo (they play at their own rate and are re-synchronised at each clip start, locate and loop wrap, so a clip of many bars drifts when the two tempos differ), streamed audio while following (silent today), a lock for a sender that sends no Start or Song Position Pointer (the song runs on the measured tempo alone), and a setting for how tightly the song is held to the clock.
- **Plugin sandbox follow-ups.** Run the sandbox on Linux and macOS for real (the wake-up and stdout redirection are compile-checked only), optional grouping of several instances in one process, and embedding sandboxed editors where the platform allows it.
- **macOS and wider Linux verification.** Ubuntu 26.04 is a main platform beside Windows; other distributions and audio setups still need checking. macOS is built, linted and tested only on GitHub Actions and has not been run on a Mac by hand. Verifying and fixing both is a priority.
- **VST3 on Wayland.** Plugin editor embedding on native Wayland (sandboxed editors already run through XWayland; in-process editors and sessions without `DISPLAY` fall back to the parameter pane). Editors that need file-descriptor handlers now run on Linux; they still need checking with more real plugins.
- **Signed builds.** The pipeline is wired (Authenticode or Azure Trusted Signing, Developer ID signing with notarisation, a GPG signature of the checksums) and skips each step until its secrets exist; what is left is to obtain the certificates (a Windows code-signing certificate or an Azure signing account, an Apple Developer ID account, a GPG key), add them to the `release-signing` environment and confirm the first signed release on real machines. Until then the builds are unsigned.

## Phase 2: The sequencer

- **Automation recording follow-ups.** A touch that starts at the press instead of the first move (needs a press and release signal from every control, plugin windows included).
- **MIDI controller data follow-ups.** Controller lanes without a note clip, and MPE (per-note expression) lanes.
- **Loop recording and takes follow-ups.** Takes for automation passes (a loop recording of automation still lays layered clips), and a saved link between the take groups of several tracks (today the link is the track selection).
- **Quantize and groove follow-ups.** Controller lane points that move with their notes, a groove from a MIDI file or an audio loop, and per-note-length quantize options (a length per note, not one for the whole selection).
- **MIDI file follow-ups.** Per-note expression (MPE) kept, a groove taken from a MIDI file (see Quantize and groove follow-ups), and typing the bytes of a SysEx message (the piano roll adds General MIDI System On, moves, deletes and clears messages).
- **Arrangement restructuring follow-ups.** Scaling a whole selection about its start by dragging its outer edge (an Alt+drag scales each clip about its own fixed edge), joining clips of different files by rendering them into one, and warp markers kept when audio clips join.
- **Rack editing follow-ups.** The "+" handles inside an unfolded container, a Create submenu that lists the device types and not only the three families, replacing a device by dragging a row of the device browser onto a track header (a library item can be dropped there today), and a context menu item to replace a device.
- **Track organisation follow-ups.** Routing the tracks of a folder to an output bus and a folder-level fader (see Phase 4).
- **Recording and editing follow-ups.** The masked parts of a looped clip dimmed in the piano roll (clips without a loop are today), and the inspector's fade unit remembered between sessions.
- **Automation lane and gesture follow-ups.** Extend to Next and Previous Clip for audio clips (it works on note and automation clips today), a range selected across several lanes, and a way to give a lane a static value from its own handle (today it comes from a control).
- **Note lane follow-ups.** Recording to several lanes at once (today a take goes to the one selected lane), and an S button on the chip of lane 0 (the header's second line is full: use the Solo Lane menu item).

## Phase 3: Audio

- **Time-stretch follow-ups.** Warp markers are edited by hand in the audio clip editor's Slice mode; still to come are the Vocal and Comp modes of the editor, tempo detection, Warp Loop as N Bars, Quantize Audio and slicing for a reversed clip (a reversed clip can be warped and transposed, but those still refuse it); a real-time stretcher that keeps the pitch (WSOLA: the preview that plays before a clip's buffer is rendered resamples through the warp markers, so a transposed clip is at the wrong pitch until the buffer is ready); formant-preserving pitch shift; stereo-linked phase locking in the Tonal mode; and warping streamed assets without holding the rendered clip in memory (the cache holds 512 MiB).
- **Freeze and bounce follow-ups.** Freezing a container instrument or a container effect in the chain, a freeze that bakes the sends or the whole channel strip into the render as an option (today the strip and the sends are never frozen and stay live), a render that follows tempo changes (today the tempo is locked while a track is frozen), freezing with in-process plugins (today the sandbox is needed), and a latency-compensated mix (a frozen track is aligned to the others but the mix is that much earlier).
- **Stem and selection export follow-ups.** Per-strip stems in WAV, AIFF and FLAC with dither, stems between the locators and a loudness report are done. Still to come: MP3 (held back until its licence is settled) and exporting a time selection (today the range is the one between the locators).
- **Audio to notes follow-ups.** Polyphonic extraction (chords and several voices), a re-attack of one pitch with a shorter dip in level than 20 ms, a snare struck with a hat (a hit is one drum, except a kick with a hat), and a drum machine track with the pads filled from the audio.
- **Spectrum and metering follow-ups.** A spectrogram, a stored reference curve, a loudness history graph with the range and a target line, the K-weighting, a 16384-point FFT with smoothing across bins and the display settings as user presets are done. Still to come: the same meters as console panels (a spectrum and a phase meter on a channel or a bus without an insert; today they are devices in a chain, and the console keeps its peak and RMS meters), a second device as the reference curve, meters for plugin devices (they have no scope tap), and FFT sizes above 16384.

## Phase 4: Mixing and control

- **Mixer groups follow-ups.** Automation of the group fader (a group is not a device today, so its level is not a lane target; it needs a device or a new lane target kind), groups of groups, a VCA that routes its members to a bus (a group bus), and a group chip on the device headers of the rack.
- **Console editing follow-ups.** Copying the master's settings (the master cannot be selected as a strip yet), a remote-control base for the strip surface, auto make-up and an E band mode on the strip, key-input auto-on for channels and buses, a level CV on the master, and sorting the selected device groups.
- **Channel strip upgrades follow-ups.** A delay-compensated `insert.bypass` on the strip itself (the console now bypasses the effects instead; the strip would need to be told the latency of its insert return), bypass and a B for container effects (a container has no bypass), a parallel compressor with a key input, a pre-insert tap and a choice of tap, and an EQ or saturation on the parallel path.
- **Snapshots follow-ups.** Snapshots that capture the output routing and the insert chains' members, and snapshot recall as an automation lane (a recall at a marker is done, but a lane would also move with the arrangement and could be drawn).
- **MIDI learn and control surface follow-ups.** Several surfaces at once, a generic driver, command mappings, NRPN and RPN sources, MMC input as a transport, the mapping panel's port and channel fields and the preset of one device are done. Still to come: the older hardware-user-interface protocol (HUI) and other surface protocols, OSC as a transport for surfaces and tablets, level meters, flip and the function keys on the eight-fader driver, a second unit (an extender) and a choice of what the V-pots drive (sends, plugin parameters), mapping the parameters of a plugin whose editor window is open (today the parameter pane, the console and the rack are learnable), a merge group for the tempo and for several controls moved at once, an MMC device number and a switch to turn MMC off per port, and NRPN and RPN sources on a control surface's own driver (the generic driver feeds them like a port).
- **Macro and parameter workflow follow-ups.** Per-track macro banks made for you (today a bank is a rack device, and the right-click menu uses the current bank), macros that drive the params of a container's inside or another bank's macro (the container keeps its own macros), a curve other than linear in the plain value (the cutoff moves linearly in Hz), a smoothing time per assignment, a direct edit of a driven param that moves its range instead of being refused, an automation lane on a driven param that the macro scales, a macro that morphs between two values of several params (a snapshot of a chain), assigning by dragging a knob onto a macro, a range edit by dragging in the panel and a numeric entry, macros and assignments in device presets, following the selection from the piano roll and the sample editor, lanes for effects and channel strips without a macro (a track needs a notes input today), saved and recent searches, search by value or by what has automation, a search that also lists clips, markers and tempo, and the search of a parameter pane reaching a plugin's params that the project has not saved a layout row for.
- **Feedback routing.** A supported way to route audio back on itself (with a mandatory delay stage) instead of the current rejection of loops.

- **Utility and CV.** Done: an LFO, a CV mixer and merger, a splitter and an attenuator and inverter (the CV Split/Merge device), CV math (add, subtract, multiply, minimum, maximum, absolute, scale and offset), a quantizer that uses the piano roll's scales, a sample-and-hold with a trigger, free or tempo clock, a slew limiter with separate rise and fall, a gate and trigger processor (logic, divide, delay, length, trigger out) and an audio-rate envelope follower (peak or RMS, attack and release, CV and gate). Still to come: custom scales and hysteresis on the quantizer, a delay and length in note values on the gate processor and a track-and-hold mode.
- **Pattern and note tools.** Done: a note filter (transpose and key and velocity filters), a key and chord device, a note repeater and a note delay, a CV sequencer with two curve rows and chained patterns, a drum generator, a bypass on every player, and players that stack on an instrument. - **Instruments.** Done: a wavetable synth, an FM synth, a granular sampler, a monosynth with a modulation matrix (Mono Bass) and a semi-modular synth built from the CV devices. Still to do: a physical-modelling instrument and an organ.

## Phase 6: Library and projects

- **Library of devices, patches and projects.** Done: the browser lists the built-in devices and the patches, containers, clips and projects of a library folder; Save to Library writes the selected devices, a container or a note clip with their samples; items load by double click or drag as one undo step, and projects open after the unsaved-changes question. Still to come: factory content, previews of clips and patches, and deleting items from the browser.
- **Start screen.** Templates and a Default Song are done (File > New from Template), and so is the recent-projects list (File > Open Recent, and an option to reopen the last project at start-up). A start screen that offers them is still to come.
- **Collect and relocate.** A project archive (`.atomikz`) packs a project with its audio, and relinking by folder repairs a project that moved, which covers part of this. Still to come: copying every file a project uses into its bundle in place, and relocating a project without breaking its links.
- **Song information follow-ups.** The title, author and notes of a song are done (File > Song Information). A version history inside the project is still to come.
- **Several songs follow-ups.** Songs open in windows of their own, one of them with the audio and the MIDI keyboard. Still to come: moving clips, devices, channels and patches between open songs, separate Input Focus and Play Focus buttons on the interface panel, recovery that offers a second song's snapshots after a crash, the library and the recent list shared live between songs, and a session of the MCP server with more than one song.

## Phase 7: Ecosystem and device parity (last)

This phase comes last on purpose: it builds on everything above and on a stable public API.

- **A stable device SDK.** A versioned, documented interface and a package format so that third parties can write and distribute devices that run natively in the rack, with their own front and back panel, parameters, CV and note sockets, and presets. This extends [docs/EXTENDING.md](docs/EXTENDING.md).
- **Device packages and a store-less installer.** Install, update and remove device packages from a folder or an archive, with signature and version checks.
- **Factory device parity.** Fill the remaining gaps in the factory set so that each usual category of device (instruments, effects, players, utilities) has at least one original design, and add the deeper variants that earlier phases only started.
- **Matching other devices.** Equivalents of well-known devices and device formats from other platforms, written as original work: a parameter-compatible mode where it helps users move their patches, and importers for patch files that are openly documented. Anything that needs proprietary data stays out (see HI-4 in the README).
