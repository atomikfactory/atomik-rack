# Roadmap

This is a list of intentions, not promises. There are no dates. The phases are in rough priority order, but items inside a phase are not ordered. Ideas and help are welcome: open a discussion or an issue before starting something big.

Design questions that shape several items (plugin batching, ASIO licensing, delay compensation, the patch format, modulation, note naming, format cadence and more) are recorded with their options and status in the [decision log](docs/DECISIONS.md).

## Phase 1: Stability and platforms

- **Sync follow-ups.** Audio clips stretched to the followed tempo (they play at their own rate and are re-synchronised at each clip start, locate and loop wrap, so a clip of many bars drifts when the two tempos differ), streamed audio while following (silent today), a lock for a sender that sends no Start or Song Position Pointer (the song runs on the measured tempo alone), and a setting for how tightly the song is held to the clock.
- **Plugin manager follow-ups.** Done: the table, the filters, favourites, tags, Disable, the quarantine and the rescan. Still to come: a category read from the plugin's own feature list (a plugin that only analyses is listed as an effect), the quarantine reason in the table, keeping a quarantined plugin out of the projects that use it, and a tag cloud in the browser instead of the `#tag` search.
- **Plugin sandbox follow-ups.** Run the sandbox on Linux and macOS for real (the wake-up and stdout redirection are compile-checked only), optional grouping of several instances in one process, and embedding sandboxed editors where the platform allows it.
- **Linux packages follow-ups.** The AppImage and the Flatpak bundle are built by the release and nightly workflows and
  checked on a runner, but not yet run on real machines of several distributions (see the checklist in
  [RELEASE-TESTING.md](docs/RELEASE-TESTING.md)). Still to come: a Flathub submission (it needs screenshots of the
  program in the metainfo and a manifest that builds from the source archive), plugin folders outside the home folder
  for the Flatpak (system-wide plugins are not visible in the sandbox), AppImage updates through its own update
  information, an ARM64 build, and an older build machine so the programs run on older distributions.

- **Instrument patches.** Done: a single-device patch applied in place, saved, stepped and browsed with audition from a patch strip on every device. - **Sound analyst.** Done: Analyze > Sound Analyst takes an audio file (dropped on the panel or picked) and measures it on a worker: the amplitude envelope (attack, decay, sustain level, release and how long the note is held), the brightness over time (the spectral centroid), the pitch over time (the audio-to-notes tracker, or unpitched), the harmonic profile (a pure tone, all harmonics, odd harmonics only, inharmonic or noise) and the noise share, and draws the three curves with the numbers. A starting patch is proposed by rules written as constants: the poly synth on one oscillator (a sine, saw, square or triangle) for a harmonic sound, the FM synth for an inharmonic one, the poly synth as a noise voice (high-pass or band-pass) for noise or an unpitched sound, with the amp envelope, a filter envelope for the brightness movement, a pitch envelope and the noise level set from the measurements. Make Patch adds the patch on a new track with a one-note clip, in one undo step; Match renders the patch as it is now, so a patch changed by hand can be measured again. Still to come: a chord or several notes in the sound (one note is analysed), a patch for the sampler or the wavetable synth, a choice between several candidate synths with their matches side by side, a correction of the envelope times and the filter resonance after the first render, effects (chorus, delay, reverb) recognised in the sound, an audio clip of the song as the source, and a lead time before the sound that is kept.

## Phase 7: Ecosystem and device parity (last)

This phase comes last on purpose: it builds on everything above and on a stable public API.

- **A stable device SDK.** A versioned, documented interface and a package format so that third parties can write and distribute devices that run natively in the rack, with their own front and back panel, parameters, CV and note sockets, and presets. This extends [docs/EXTENDING.md](docs/EXTENDING.md).
- **Device packages and a store-less installer.** Install, update and remove device packages from a folder or an archive, with signature and version checks.
- **Factory device parity.** Fill the remaining gaps in the factory set so that each usual category of device (instruments, effects, players, utilities) has at least one original design, and add the deeper variants that earlier phases only started.
- **Matching other devices.** Equivalents of well-known devices and device formats from other platforms, written as original work: a parameter-compatible mode where it helps users move their patches, and importers for patch files that are openly documented. Anything that needs proprietary data stays out (see HI-4 in the README).
