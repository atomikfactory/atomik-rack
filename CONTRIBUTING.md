# Contributing to Atomik Rack

Thank you for helping. This document lists the rules every contribution must follow. They exist to protect the four hard invariants described in the [README](README.md#hard-invariants).

Before you start:

1. For anything larger than a small fix, open an issue first so we can agree on the approach.
2. Read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), especially the crate dependency rules, and [docs/TESTING.md](docs/TESTING.md).

All participants follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## 1. Original work policy

- Submit only code, data and assets that you wrote yourself, or that are available under a licence compatible with GPL-3.0-or-later. Say where third-party material comes from (in the commit message or pull request) and keep its licence notice.
- Do not paste code, data, presets, samples, graphics, fonts or strings from proprietary products, from their binaries, or from material you are not licensed to copy. Do not submit anything derived from decompiled or disassembled software.
- Algorithms from public textbooks, papers and standards are welcome; cite them in a comment.
- Example audio and fixtures must be generated by project code or be your own work released under a compatible licence (CC0 is preferred).
- If you have doubts about the origin of something in the repository, report it privately (see [SECURITY.md](SECURITY.md)) and do not repost the material.

## 2. Developer Certificate of Origin (DCO)

Every commit must be signed off:

```sh
git commit -s -m "engine: reject cables between different socket kinds"
```

This adds a line like the following to the commit message:

```
Signed-off-by: Your Name <you@example.com>
```

By adding it you certify the [Developer Certificate of Origin 1.1](https://developercertificate.org/). In short, you state that:

- you wrote the contribution, or have the right to submit it under the project's licence (GPL-3.0-or-later); and
- you understand that the contribution and your sign-off are public and kept permanently.

The DCO is not a copyright assignment. You keep your copyright; you license your contribution under the project licence. If you forgot to sign off, fix it with `git commit --amend -s` (last commit) or `git rebase --signoff main` (several commits).

## 3. Workflow

- Work on a branch in your fork (or a feature branch) and open a pull request against `main`. **Do not push directly to `main`.**
- Keep each pull request focused on one change, fill in the [pull request template](.github/PULL_REQUEST_TEMPLATE.md), and link the issue.
- Update the docs when behaviour or public APIs change.
- QA what you changed before you ask for review: for a change to the sound or to what the app shows, follow the recipes in [docs/MCP.md](docs/MCP.md) (bounce and compare against the previous render, drive the app headlessly, read the screen) and say in the pull request what you ran and what it showed. The `atomik-mcp` server automates them for an MCP client; `atomik-render` and the headless tests do the same by hand. This is evidence, not a substitute for tests: behaviour that matters still gets a headless test (section 5).
- Respect the crate dependency rules in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#1-crates-and-the-dependency-rule).
- On Windows, set `git config core.autocrlf false` so line endings stay as the repository stores them.

### Commit messages

Use a short imperative subject (about 70 characters), optionally prefixed with the area (`engine:`, `ui:`, `model:`), then a blank line and a body that explains what changed and why. The `Signed-off-by` line goes last.

## 4. Code style and quality gates

A pull request is merged only when all of these pass locally and in CI:

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo deny check
```

- `rust-toolchain.toml` pins the toolchain; do not change it in a feature PR.
- Formatting is `rustfmt` with the repository's `rustfmt.toml`. Run `cargo fmt --all` before you commit.
- Lints are configured in the root `Cargo.toml` and `clippy.toml`. Do not silence a lint without a local `#[allow(...)]` and a comment that justifies it.
- `cargo deny` enforces the dependency licence allow-list (GPL-3.0-compatible licences only), bans and security advisories. New dependencies must pass it and should be discussed in the PR.
- `unsafe` code is denied workspace-wide. Any exception needs a documented, reviewed justification and a `SAFETY:` comment.
- `Cargo.lock` is committed. Public items are documented.

## 5. Tests first

Every change to production behaviour comes with tests, and writing the test first is encouraged.

1. **Red.** Write a test that expresses the new behaviour or reproduces the bug. Run it and watch it fail for the expected reason.
2. **Green.** Write the smallest change that makes it pass.
3. **Refactor.** Clean up with all tests green.

Guidelines:

- Every new production type or public function is introduced by a test.
- Bug fixes include a regression test that fails without the fix.
- Prefer property tests (`proptest`) for numerical code, parameter ranges and anything with "for all inputs" semantics.
- Tests must be deterministic: no sleeps, no wall-clock time, no unseeded randomness, no network. Tests that need hardware or a real plugin are `#[ignore]`d (see [docs/TESTING.md](docs/TESTING.md)).
- A change to `atomik-mcp` follows [docs/MCP.md](docs/MCP.md#extending-the-server): every tool has an argument-validation, a path-policy and a result test through `Server::call_tool`.
- Goldens (display lists, render fingerprints, the keyboard reference) are regenerated with `ATOMIK_UPDATE_GOLDEN=1` and the diff is reviewed; see [docs/TESTING.md](docs/TESTING.md).

## 6. Real-time safety (HI-1)

Code that runs on the render path (`Device::process`, `Engine::render`, and everything they call) must never:

- allocate or free memory (no `Vec::push` that may grow, `Box::new`, `String`, `format!`, `clone()` of heap data, `collect()`);
- lock (`Mutex`, `RwLock`), wait on a condition variable or channel, or block in any other way;
- do I/O, including printing and logging;
- drop anything that frees heap memory.

Instead:

- allocate everything in `prepare` or at compile time, on the non-real-time side;
- use fixed-capacity buffers and drop (and count) overflow rather than grow;
- communicate with the non-real-time side through the wait-free queues provided by the engine;
- hand retired objects back to the non-real-time side to be dropped there.

**Proving it.** Each test binary installs the counting allocator once:

```rust
atomik_testkit::install_alloc_guard!();
```

Engine tests wrap render calls in `atomik_testkit::no_alloc::assert_no_alloc(|| ...)`, and device tests use `atomik_testkit::harness::DeviceHarness`, which guards every `process` call. A test fails if the closure allocates, reallocates or frees memory. New render-path code needs a test that runs it under the guard. How the invariant is enforced is described in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#8-how-the-hard-invariants-are-enforced).

## 7. Determinism (HI-2)

The same patch and the same input must render to bit-identical output on every run and with every host block size.

- **No hash-ordered collections.** `HashMap` and `HashSet` are banned by `clippy.toml`. Use `BTreeMap`, `BTreeSet` or `Vec` indices.
- **No time sources.** `Instant::now` and `SystemTime::now` are banned in production code. Nothing may depend on wall-clock time or thread timing.
- **Seeded randomness only.** Use the project's seeded RNG (`atomik-dsp`), seeded from the patch seed and the device instance id. Do not use the `rand` crate, OS entropy or addresses as seeds.
- **Deterministic ordering.** Where ordering is a choice (for example topological sort ties), break ties by a stable key such as the device instance id.
- **Initialise all state** in `prepare` / `reset`; never rely on leftover buffer contents.
- Be careful with floating point: do not let results depend on block boundaries or iteration order.

Tests for new devices and engine features should include a block-size invariance check where relevant.
